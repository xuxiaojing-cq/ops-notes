## 一、为什么做这个

前面 21 天学的是"怎么让系统跑起来、怎么发布、怎么回滚"。这一天的题目换了个方向：**故障发生后，怎么让人更快地看懂发生了什么。**

真实场景是这样的：一次故障，Prometheus 触发几十条告警，Alertmanager 按路由分发给不同的群。值班的人面对的是刷屏的通知，要在脑子里完成三件事：

1. 这几十条里，哪些其实是同一回事？
2. 谁是因、谁是果？
3. 我第一条命令该敲什么？

这三件事都可以自动化。这也是我往 AI 方向转的第一个练手项目——**不是学炼丹，是把 AI 当成一个新的应用类型来工程化**。

## 二、最重要的设计决定：不把告警直接丢给大模型

最直觉的做法是：告警 JSON → 大模型 → "分析原因"。生产上这样做会死，三个原因：

| 问题 | 后果 |
|---|---|
| 告警风暴时一次几百条 | token 爆炸、费用失控、延迟不可控 |
| 模型超时 / 限流 / 网关故障 | 告警通道跟着挂，这是 P0 事故 |
| 模型编造根因 | 比没有诊断更危险，会把人带向错误方向 |

所以分成两层：

```text
Alertmanager webhook
   ↓ normalize   拆成扁平的单条告警（不做推断）
   ↓ aggregate   聚成「事件」，几十条 → 几个        ← 确定性降维
   ↓ diagnose    规则给出根因候选 + 证据 + 验证命令  ← 必然有输出
   ↓ llm         可选：只在给定候选里排序和表达      ← 可降级
   ↓ render      事件卡片 / JSON / 退出码
```

**规则层是底座，模型是增强。** 模型挂了，规则层照样给出完整结论，并且会打印降级原因。

## 三、实测结果

### 输入：一个 7 条 payload 的告警风暴

`fixtures/synthetic-storm.json` 里放了 7 个 webhook payload，共 15 条告警，模拟同时发生的多个故障。其中 1 条是真实记录（`real-nodeexporter-down.json`，来自 Day 4 搭 Prometheus 时实际收到的 payload），其余为构造数据。

### 输出：6 个事件

```text
事件数: 6  退出码: 2
 - common_cause | ServiceDown 同时影响 3 个实例            | R002-common-cause
 - single_host  | web04:9100 出现 3 类告警                  | R001-scrape-side-failure
 - single_host  | nfs01:9100 出现 1 类告警                  | R006-disk-space
 - flapping     | 告警抖动：HighMemoryUsage（3 次状态翻转）  | R008-flapping
 - single_host  | db01:9100 出现 2 类告警                   | R003-load-io-bound
 - unscoped     | Alertmanager 截断标记                     | R009-truncated
```

15 条告警压成 6 个事件，每个事件都有结论。退出码 2 表示有 critical，可以被脚本接住。

对照不聚合的情况：值班的人要在 15 条里自己找关联，其中 `ServiceDown × 3` 还要自己意识到是同一回事。

## 四、三个真实 bug（这天的核心价值）

### bug 1：假共因，把诊断结论改掉了

**现象。** 第一版跑出来 7 个事件，其中两个明显不对：

```text
事件4: HighLoadAverage 同时影响 2 个实例（db01 + web04）  ← 假的
事件6: db01 只剩 HighDiskIOWait → "没有规则命中"          ← IO 瓶颈没诊断出来
```

db01 是「负载 + IO 等待」，本该命中 R003（IO 瓶颈）。但 db01 和 web04 **两台机器毫无关系**，唯一的共同点只是都有 `HighLoadAverage`。

**根因。** 聚合时我写的规则是「同一个 alertname 出现在多个实例上 → 共因」，然后把那些告警从各自的上下文里**抽走**合并。结果 db01 的 `HighLoadAverage` 被拽进假共因组，剩下的 `HighDiskIOWait` 单独成事件，凑不齐「负载 + IO」的组合，规则自然命中不了。

⭐ **这是这次最值得记的一条：聚合方式能悄悄改变诊断结论。** 它不是"少诊断了一点"，而是给出了一个错误的排查方向——让人去查一台和故障无关的机器。

**修法。** 判共因不能只看共有告警，还要看**剩余告警是否一致**：

```python
def _companions_consistent(hosts, shared_name, host_names):
    """共有告警之外，各实例的剩余告警种类是否一致。"""
    signatures = {frozenset(host_names[h] - {shared_name}) for h in hosts}
    return len(signatures) == 1
```

- 剩余全为空（发布打挂三台，症状完全一样）→ 真共因，仍能识别
- 剩余各不相同（db01 有 IO、web04 有采集故障）→ 不是共因，不合并
- 剩余完全一致（都是「负载 + IO」）→ 更像同一套变更下发，算共因

修完从 7 个事件变 6 个，db01 正确命中 R003，置信度「高」。

**顺带加了一条判据。** 共因的置信度现在会看**组内触发时间跨度**：真实发布事故的告警往往在几秒内一起炸，跨度上百秒说明它们只是恰好落在同一个聚合窗口。实测三台 ServiceDown 跨度 8 秒 → 高；如果跨度大就自动降到中或低。

### bug 2：接收器把合法输入判成非法

**现象。** webhook 接收器日志：

```text
已存盘 /tmp/ai-captured/xxx-payload.json
payload 顶层不是对象，已存盘但跳过分析     ← 合法数据被跳过
```

**根因。** 我的 fixture 顶层是**数组**，而接收器只认单个对象。CLI 支持数组、server 不支持，两边行为不一致。Alertmanager 实际发的是单个对象，但回放抓取的一批 payload 时数组很常见。

**修法。** 两种形态都吃：

```python
payloads = payload if isinstance(payload, list) else [payload]
payloads = [p for p in payloads if isinstance(p, dict)]
```

### bug 3：无状态分析让抖动检测彻底失效

这个比前两个更严重——**功能在真实场景下根本不会触发**。

**现象。** 逐条推送 web05 的 4 次状态翻转（firing → resolved → firing → resolved），每次分析都只报「内存压力」，抖动从头到尾没被识别。

但在 CLI 里一次性回放同样数据，抖动能被检出。

**根因。** 接收器是无状态的。**Alertmanager 永远是一次推一条**，不会给你完整序列，所以单次 POST 里永远看不到状态翻转。

**修法。** 加一个内存滑窗，保留最近 10 分钟收到的告警，每次都把当前 payload 并进历史再分析：

```python
FLAP_WINDOW_SECONDS = 600
MAX_FLAP_HISTORY = 2000
_flap_history: list[tuple[datetime, Alert]] = []   # 存 (接收时间, Alert)
```

同时只输出与**本次 payload 相关**的事件——值班的人关心的是"刚发生了什么"，历史窗口只用于补足抖动判断。

**修的过程里又踩了一个。** 第一版用告警的 `starts_at` 判断超期，结果一条持续了几小时的告警刚推过来就被当"过期数据"清掉，聚合拿到空列表，**分析输出直接消失**。过期判断必须用**接收时间**，不是告警自身的触发时间。

修复后的实测是**渐进式**的，符合真实使用：

```text
第 1 条 POST (firing)   → 内存压力（中）
第 2 条 POST (resolved) → 内存压力（中）
第 3 条 POST (firing)   → 内存压力（中）
第 4 条 POST (resolved) → 告警抖动：HighMemoryUsage（3 次状态翻转）（高）   ← 攒够了才认得出来
```

抖动本来就得观察一段才认得出来，不该期望第一次就报。

## 五、归因规则：先问数据可信吗，再问哪里坏了

规则顺序是刻意的，`R001` 必须排在最前：

| 规则 | 判断 | 为什么重要 |
|---|---|---|
| R001 | 采集侧故障 | exporter 挂了会让同机所有指标告警，看着像整机崩溃，业务可能完全正常。**先问数据可不可信** |
| R002 | 横向共因 | 多实例同时同症状 → 根因在公共部分，**逐台排查是纯浪费时间** |
| R003 | 负载 + IO 等待 | 进程卡在 D 状态等 IO，负载计入但 CPU 不忙 |
| R004 | 只有负载异常 | 可能是进程堆积、容器限流，或阈值贴着常态水位 |
| R005 | 内存压力 | 区分泄漏（RSS 单调上升）与容量不足（稳定高位） |
| R006 | 磁盘空间 | 空间 / inode / 已删除但被持有，处置方式完全不同 |
| R007 | 单实例服务不可用 | 先分「进程没了」还是「进程在但不响应」 |
| R008 | 告警抖动 | 会被 resolved 掩盖，必须单独拎出来 |
| R009 | payload 被截断 | 影响面被低估，不能基于截断数据判断 |
| R010 | 证书到期 | 多实例同时到期通常是续期机制坏了 |
| R011 | 错误率升高 | 灰度期间整体错误率会被权重稀释 |

R001 在实测里的表现：

```text
web04 同时有 NodeExporterDown + HighLoadAverage + HighMemoryUsage
  ↓
采集侧故障：NodeExporterDown
依赖该采集的指标告警（数据可能已中断）：HighLoadAverage, HighMemoryUsage   ← 明确标成"不可信"
  ↓
判断顺序：先问「数据可信吗」，再问「哪里坏了」
```

⚠️ **这个证据描述本身也修过一次。** 第一版写成"事件内含采集侧告警：HighMemoryUsage, NodeExporterDown"，把 `HighMemoryUsage` 和采集故障并列了——但它明明是该被这条规则**排除**的对象。方向性描述写错，比没有证据更误导。

### 置信度为什么只有三档

规则是启发式。写 `confidence: 0.87` 是假精确，那个数字没有任何统计来源。所以只分高/中/低，并且**每条规则必须给出判别方法**（"如果不是这个原因，你会看到什么"）。真正降低不确定性的是去跑验证命令，不是模型给的分数。

有一条测试专门遍历所有规则，断言"给了结论就必须给验证方法"。

## 六、LLM 层：幻觉用工程手段约束

不靠"提示词写得好"，靠三道闸：

1. **输入闭集**：prompt 里只有 payload 事实 + 规则候选，明确禁止引入候选之外的根因
2. **输出结构化**：要求固定字段的 JSON（自由文本无法校验）
3. **输出校验**：解析失败、引用了不存在的 `rule_id`、缺字段 → 一律判失败并降级

第 3 条里最关键的是 **rule_id 白名单**：模型一旦开始编造根因，必然要造一个 ID，而 ID 不在白名单里就会被拦下。

### 用本地 mock 验证四条路径

不依赖外部网络，验证的是"我们的校验逻辑拦不拦得住"：

```text
场景 1：合规 JSON
  ok=True  headline=三台实例同时不可用，疑似发布导致  usage={'input_tokens': 500, 'output_tokens': 80}

场景 2：编造候选外的 rule_id          ← 幻觉
  ok=False  degraded_reason=...引用了候选之外的 rule_id: ['R999-disk-full-invented']

场景 3：返回非 JSON 的散文
  ok=False  degraded_reason=...解析失败: 输出中找不到 JSON 对象

场景 4：套了 ```json 代码块
  ok=True   headline=共因故障，优先查变更       ← 容错成功
```

### 真实调用

```text
**🤖 AI 解读**（claude-opus-4-1-20250805，9846ms）

> 3个ci-web实例8秒内同时宕机，高度怀疑共因故障（发布/依赖/配置/网络）

3个实例在8秒内触发相同告警ServiceDown，时间高度集中，符合共因故障特征。
单机独立故障不会如此同步。需排查公共依赖或近期变更。

⚠️ 尚不确定：尚不清楚具体是哪类共因（发布/配置/依赖服务/网络），
需查变更记录和依赖连通性才能定位。
```

值得注意的三点：它没有编造根因，只用了给定的候选；它如实说出了不确定的地方；它给出的命令是从 verify 列表里挑的，没有自己发明。

## 七、真实调用撞到的三个环境问题

这三个都不是逻辑 bug，是"代码在本机跑不通"，正好对应真实交付里最常见的三类问题。

### 1. SSL 证书校验失败

```text
CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate
```

**原因**：macOS 上 Framework 版的 Python 不自动读系统证书库。

**处理**：按优先级找 CA 包（环境变量 → certifi → 系统 CA 文件），**绝不为了跑通而关闭校验**——告警内容里有主机名和业务指标，关掉校验等于把它们暴露给中间人。都找不到时让请求失败并降级，而不是降级安全性。

⭐ 这里值得记的是：**它没有崩，而是正确降级并打印了原因。** 降级设计在这一刻得到了验证。

### 2. 模型名已废弃

```text
HTTP 400: The requested model has been deprecated and is no longer available.
```

硬编码的默认模型名会随供应商下线旧版本而失效。改成支持 `AI_MODEL` 环境变量覆盖，并在代码注释里写明"这个失败会正常降级，但要记得定期确认默认模型名仍然可用"。

### 3. 网关强制返回 SSE 流

```text
content-type: text/event-stream;charset=UTF-8
```

我按普通 JSON 解析，报 `Expecting value: line 1 column 1`。有些网关无视请求体里的 `stream` 参数，一律返回流式响应。

**处理**：按 content-type 分支，SSE 就走 `data:` 行解析，只取 `content_block_delta` 里的文本增量，其他事件（message_start / ping / message_stop）忽略。不需要实现完整流式状态机——本工具的用法是"一次性拿完整结果"，不是边生成边展示。

## 九、面试答法

> **问：你怎么把 AI 用到运维场景里？**
>
> 我做了个告警聚合归因工具。不是把告警直接丢给大模型——那样告警风暴时 token 和延迟都不受控，而且模型一挂告警通道就跟着挂，这是 P0。
>
> 我的做法是分层：先用确定性代码把几十条告警聚成几个事件，再用规则库给根因候选和验证命令，最后模型只负责在给定候选里排序和用人话表达。模型挂了就降级到规则层，而且降级原因会打在输出里，不会让人误以为模型认可了这些结论。
>
> 防幻觉不靠提示词，靠工程约束：输入只给候选、输出必须是固定字段的 JSON、并且校验返回的 rule_id 必须在白名单里。模型编造根因必然要造一个 ID，造了就被拦下。
>
> 做的时候踩到一个挺有意思的坑：我最初按"同一个告警名出现在多个实例上"判共因，结果把两台毫不相关的机器合并了，其中一个实例的 IO 瓶颈告警被拽进假共因组，剩下的单条告警凑不齐组合，规则永远命中不了。**聚合方式把诊断结论改掉了。** 后来加了约束：除了共有告警，各实例的剩余告警种类也必须一致。
>
> 还有一个是接收器的状态问题。开始写成无状态的，但 Alertmanager 永远一条一条推，单次请求里看不到状态翻转，抖动检测根本不会触发。加了跨请求的历史窗口才修好，顺带又踩了个坑：过期判断得用接收时间，不能用告警自己的 startsAt。

## 十、已知局限

| 局限 | 说明 |
|---|---|
| 规则是启发式 | 不是因果推断，结论必须靠验证命令确认 |
| 不感知变更 | 判断"是不是刚发布导致的"仍需人工关联。**这是最该补的下一步** |
| 只看 payload | 不查 Prometheus 历史曲线，无法判断趋势 |
| 无持久化 | 接收器重启后抖动历史清零；不记忆历史事件 |
| 未接通知渠道 | 只输出 stdout，没推到 IM |
| LLM 成本未测 | 每事件一次调用，告警风暴时的费用需要实测后加限流 |
| 单机验证 | 没在真实多机构环境跑过，规则库需要按实际情况补 |

## 十一、这次学到的方法论

1. **聚合方式会改变结论。** 合并规则不是"展示问题"，它决定了后续所有判断的输入。合并错了，规则再对也没用。
2. **无状态设计在流式场景下会静默失效。** 功能"能跑通"和"在真实调用模式下会触发"是两回事。CLI 回放能测出抖动，不代表线上能。
3. **降级要和功能一起测。** 这次 SSL、模型废弃两个问题全靠降级兜住才没中断，而"降级原因必须可见"这条设计原则，让问题一眼就能看见而不是被藏起来。
4. **环境差异不是意外，是常态。** macOS 的证书、网关的 SSE、模型的废弃——交付现场遇到的问题基本都是这一类，和代码逻辑无关。
5. **测试要写"防回归"，不是"提覆盖率"。** 71 个用例里最有价值的几条，都是先踩了坑再写的。
