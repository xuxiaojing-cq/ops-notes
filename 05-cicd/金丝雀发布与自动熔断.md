# 金丝雀（灰度）发布与自动熔断

> Day 21，2026-11-17。目标机为一台 ECS，nginx `upstream` 加权分流。
> 全部数据来自实际执行；失败是真实触发的（v3 镜像启动即退出 / 自建 500 服务）。
> ⚠️ 单机环境，三个后端跑在同一台机器；真实灰度通常跨机房或跨可用区，本次不覆盖。

## 一、为什么蓝绿还不够

Day 20 的蓝绿零失败，但它有个没说出口的前提：

```text
蓝绿的验证 = 自己发一个 /healthz，通了就切 100% 流量
```

**问题：很多故障 `/healthz` 查不出来。** 比如新版本在"某家机构数据量特别大"时才超时——自测永远是通的，切过去才炸。

| | 蓝绿 | 金丝雀 |
|---|---|---|
| 验证流量 | 合成请求（自己造的） | **真实用户流量** |
| 切换方式 | 一次性 100% | 逐步放量 10% → 50% → 100% |
| 坏版本影响 | 0 | **有，但限制在小比例内** |

金丝雀用"牺牲一小部分用户"换"发现合成测试查不到的问题"。

## 二、结构：一个池子，按权重分

```text
Day 20 蓝绿：两个独立后端，开关二选一
Day 21 金丝雀：三个后端放进同一个 upstream，nginx 按权重分

              ┌─ d21-stable-1 (v1)  weight=9
   流量 ──────┼─ d21-stable-2 (v1)  weight=9     合计 20
              └─ d21-canary   (v2)  weight=2     → 占 10%
```

```nginx
upstream app_pool {
    server d21-stable-1:8080 weight=9;
    server d21-stable-2:8080 weight=9;
    server d21-canary:8080   weight=2;
}
server {
    listen 80;
    location / {
        proxy_pass http://app_pool;
        add_header X-Upstream $upstream_addr always;
        add_header X-Status   $upstream_status always;
    }
}
```

`$upstream_addr` 是关键：池子模式下 nginx 自己决定发给谁，只能让它事后告诉我们。

## 三、权重是精确的，不是概率

500 次请求实测：

```text
172.19.0.2 (stable-1)  250   50.0%
172.19.0.3 (stable-2)  200   40.0%
172.19.0.4 (canary)     50   10.0%   ← 精确 10%
```

金丝雀 10.0% 分毫不差。但两个同权重的 stable 却是 50% vs 40%——

**原因是我的探测脚本有缺陷**：它发两次 curl（一次取后端、一次取状态码），只记录第一次，被丢弃的那次把轮询序列错开了。

修正成单次请求后重测：

```text
stable-1  135   45.0%
stable-2  135   45.0%     ← 完全相等
canary     30   10.0%
```

⭐ **教训：测量工具本身会干扰被测对象。** 两个同权重后端结果不等，是检验探测方法是否可靠的免费校验点。

### 不是随机，是平滑加权轮询

金丝雀命中位置的相邻间隔统计：

```text
间隔 8   出现 25 次
间隔 10  出现 18 次
间隔 18  出现 6 次
```

间隔集中在 8-10，**从未出现间隔 1**（连续两次进金丝雀）。nginx 会刻意把金丝雀请求打散。

生产意义：纯随机有概率连续几十个请求全砸进金丝雀，某个用户连点几次全失败；平滑轮询保证故障是稀疏分布的。

## 四、核心发现：两种故障，nginx 行为完全相反

这是今天最有价值的一条。用两种坏法分别测：

| 金丝雀故障类型 | 客户端看到的失败率 | nginx 是否兜底 |
|---|---|---|
| **进程崩了**（端口无人监听） | **0.0%** | ✅ 静默重试到别的后端 |
| **活着但返回 500** | **10.0%** | ❌ 原样返回给用户 |

### 为什么

nginx 的 `proxy_next_upstream` 默认值是 `error timeout`：

- **连接层面错误**（连不上、超时）→ 自动重试下一个后端
- **500 是应用层响应** → nginx 认为"服务器回答了，只是答案不满意"，原样转发

### 证据：X-Upstream 里的逗号

崩溃场景下的一条真实记录：

```text
客户端收到:  code=200
X-Upstream:  172.19.0.4:8080,     ← 逗号！
X-Status:    504,
```

逗号说明这次请求被发了两次：先给金丝雀（504 超时），再自动转给别人（200）。**用户看到 200，后台其实发生了 504。**

### 这个发现的危险之处

```text
崩溃   → 被 nginx 兜住 → 你观察不到问题 → 以为新版本没事
500    → 原样返回     → 10% 用户直接看到错误
200但内容错 → 连状态码都看不出来
```

⭐ **金丝雀必须做业务级验证，不能只看 HTTP 状态码。**

### 附带验证：容器停了，DNS 就没了

```text
docker run --rm --network d21-net curl http://d21-canary:8080/healthz
→ curl: (6) Could not resolve host: d21-canary
```

但 nginx 仍在往旧 IP 发请求——因为 **nginx 只在启动/reload 时解析一次 upstream 主机名**，之后用缓存 IP。

⚠️ **未验证项**：崩溃后金丝雀 300 次只被尝试 2 次，我最初归因于被动健康检查（`max_fails=1` / `fail_timeout=10s`）。但实验 A 是 reload 之后跑的、失败计数应已清零，仍只碰 1 次。可能是平滑轮询初始分布 + 样本量小。**未做隔离实验，不下定论。**

## 五、自动熔断闸门的第一版（有致命缺陷）

目标：把"人工盯着"变成"自动判定"。用退出码表达决策，才能被 CI / Ansible 接住。

```bash
rate=$(awk -v b="$bad" -v t="$total" 'BEGIN{printf "%.1f", b*100/t}')
if awk -v r="$rate" -v th="$THRESHOLD" 'BEGIN{exit !(r > th)}'; then
  echo "DECISION: ROLLBACK"; exit 1
else
  echo "DECISION: PROMOTE";  exit 0
fi
```

实测同一个坏版本：

```text
阈值 5%   → 失败率 10.0%  → ROLLBACK  (退出码 1)
阈值 15%  → 失败率 11.0%  → PROMOTE   (退出码 0)
```

注意两次测的是同一环境，却得到 10% 和 11%——**采样有波动，阈值定在真实值附近时判定会随机摇摆。**

### 致命缺陷：稀释效应

这个脚本测的是**整个池子**，不是金丝雀自己。实测对照：

```text
直接测金丝雀本身:  50 次失败 50 次  → 100%
同一时刻测池子:    100 次失败 9 次  → 9%
阈值设 20% 的判定: PROMOTE          ← 100% 全坏的版本被放行！
```

原因：

```text
池子错误率 = 金丝雀错误率 × 金丝雀权重
           = 100%         × 10%       = 10%
```

⭐ **一个完全不可用的版本，用看起来合理的 20% 阈值，会被判定为"健康，可全量"。**

## 六、修正：直接测金丝雀

绕过池子，直接打金丝雀容器：

```bash
code=$(docker run --rm --network "$NET" curlimages/curl:latest \
  -sS -o /dev/null -w '%{http_code}' -m 3 "http://${TARGET}:8080/healthz")
```

同样 20% 阈值的对照：

| 测量方式 | 真实 100% 坏的金丝雀 | 判定 |
|---|---|---|
| 测池子 | 测到 10% | ❌ PROMOTE（漏判） |
| **直测金丝雀** | 测到 **100%** | ✅ ROLLBACK |

健康版本对照：直测 stable-1，30 次失败 0 次，`PROMOTE`，退出码 0。

⭐ **面试点：灰度的错误率必须按"金丝雀自身"算，不能按整体算。** 若只能拿到整体指标，阈值要除以权重——10% 权重时，整体 1% 异常就相当于金丝雀 10% 异常。

## 七、完整放量流程与两次真实 bug

流程：`10% → 闸门 → 50% → 闸门 → 100%`，任一关失败就回滚。

### bug 1：回滚谎报成功

坏版本演练，闸门正确拦截并打印「已回滚」，但核实流量：

```text
失败数: 6 / 60
172.19.0.4:8080   6      ← 金丝雀仍拿着 10% 流量
```

查真实返回：

```text
nginx: [emerg] invalid parameter "weight=0" in app.conf:4
nginx: configuration file test failed
reload 退出码: 1
```

**`weight=0` 在 nginx 里是非法参数**，reload 失败、旧配置继续生效。而我的脚本写的是：

```bash
docker exec d21-nginx nginx -s reload >/dev/null 2>&1   # ❌ 错误被吞掉
```

⚠️ **这和 Day 20 是同一类事故：回滚代码自己失败了，却报告成功。** Day 20 栽在 inode，这次栽在吞 stderr。

正确做法是用 `down` 摘除后端：

```nginx
server d21-canary:8080 down;
```

并在 reload 前强制校验：

```bash
if ! docker exec d21-nginx nginx -t 2>/dev/null; then
  echo "!!! 配置校验失败，拒绝 reload"
  docker exec d21-nginx nginx -t 2>&1 | tail -2
  return 1
fi
```

修正后核实：失败 **0/60**，后端分布里金丝雀完全消失。

### bug 2：同一个坑的另一侧 —— 但这次被防住了

放量到 100% 时 stable 侧也会变成 `weight=0`，同样非法。我只修了金丝雀侧。

但结果完全不同：

```text
!!! 配置校验失败，拒绝 reload
nginx: [emerg] invalid parameter "weight=0"
权重设置失败，终止
流程退出码: 2
```

流量安全停在 50/50（15+15 stable，30 canary），**失败 0/60**。

| | 修正前 | 修正后 |
|---|---|---|
| 错误是否暴露 | ❌ 被 `2>&1` 吞掉 | ✅ 打印出来 |
| 是否谎报成功 | ❌ 打印「已回滚」 | ✅ 退出码 2 |
| 实际流量 | 仍 10% 给坏版本 | 安全停在上一档 |

⭐ **这组对照说明"前置校验 + 不吞错误"的价值：同一个 bug，一次酿成事故，一次被安全拦截。**

### 最终完整流程

统一用 `down` 处理 0 权重后，健康版本演练：

```text
---------- 阶段: 金丝雀 10% ----------
直测 d21-canary : 20 次中失败 0 次   错误率 0.0%   阈值 5%
DECISION: PROMOTE
---------- 阶段: 金丝雀 50% ----------
DECISION: PROMOTE
---------- 阶段: 金丝雀 100% ----------
DECISION: PROMOTE
===== 全量发布完成 =====  退出码 0
```

最终核实：

```text
upstream app_pool {
    server d21-stable-1:8080 down;
    server d21-stable-2:8080 down;
    server d21-canary:8080 weight=10;
}

失败数: 0 / 60
172.19.0.4:8080   60      ← 100% 走金丝雀
```

坏版本演练则在第一关被拦，退出码 1，回滚生效。

## 八、三种发布方式的完整对比

| | 原地替换(D19) | 蓝绿(D20) | 金丝雀(D21) |
|---|---|---|---|
| 停机 | 3.489 秒 | 0 | 0 |
| 坏版本影响 | 全部用户 | **0** | **权重比例内** |
| 验证流量 | 合成 | 合成 | **真实** |
| 资源 | 1x | 2x | 1x + 金丝雀 |
| 回滚速度 | 数秒 | 0.19 秒 | 改权重即可 |
| 能发现的问题 | — | 启动类故障 | **真实流量才暴露的故障** |

**取舍：** 蓝绿影响为 0 但验证是合成的；金丝雀有小比例影响但验证是真实的。两者不互斥——实际可以先蓝绿验证启动，再金丝雀放量。

## 九、面试答法

> **问：灰度发布怎么做？**
>
> nginx upstream 按权重分流，比如金丝雀 weight=2、两个稳定版各 weight=9，实测精确 10%，而且是平滑加权轮询，会把金丝雀请求打散，不会连续命中。
>
> 关键是判定逻辑。我踩过一个坑：如果按整个池子的错误率判定，会被权重稀释——金丝雀 100% 全坏，池子整体只有 10% 异常，设个 20% 的阈值就会把完全不可用的版本判为健康放行。所以错误率必须按金丝雀自身算，或者把阈值除以权重。
>
> 还有一点容易漏：nginx 的 `proxy_next_upstream` 默认只对连接错误和超时重试。金丝雀进程崩了，nginx 会静默转给别的后端，客户端看到 200，你根本观察不到问题；但返回 500 就会原样返回给用户。所以不能只看状态码，要做业务级验证。
>
> 回滚这块我出过一次事故：用 `weight=0` 摘后端，但那是 nginx 的非法参数，reload 失败了，而脚本把 stderr 重定向到 /dev/null，于是打印「已回滚」但流量照旧。正确做法是用 `down` 参数，并且 reload 前先 `nginx -t` 校验、失败就拒绝执行。

## 十、本次未覆盖

- 按用户/地域/Header 分流（`map` + `split_clients`），而非纯权重
- 会话粘滞：同一用户在新旧版本间跳来跳去的一致性问题
- 自动放量（当前每阶段靠脚本串行，未接 CI）
- 业务级指标判定（当前只看 HTTP 状态码）
- nginx 被动健康检查参数的隔离验证（见第四节未验证项）
- 金丝雀期间的数据兼容（新旧版本同时写库）
- 网关自身高可用（当前 nginx 单点）
