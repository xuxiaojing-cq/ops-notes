# 蓝绿发布与流量切换

> Day 20，2026-11-05。目标机为一台 ECS（Ubuntu 22.04，1.6G 内存），nginx 作流量网关。
> 全部数据来自实际执行的探测日志，失败是真实触发的（v3 镜像缺 `APP_GREETING` 会退出）。
> ⚠️ 单机环境，蓝绿两套跑在同一台机器上；真实蓝绿通常跨机器或跨集群，本次不覆盖跨机场景。

## 一、为什么需要蓝绿

Day 19 的部署方式是**原地替换**：

```text
docker rm -f 旧容器  ──X 空窗期 X──  docker run 新容器 → 等健康检查
                        ↑ 这段时间端口上没有任何进程监听
```

两个问题：

| 问题 | 后果 |
|---|---|
| 替换期间服务不可用 | 用户请求直接连接失败 |
| 验证发生在流量之后 | 新版本坏了，用户先受影响，再回滚 |

蓝绿把顺序反过来：**先把新版本起好并验证通过，再切流量，旧版本不删。**

```text
blue (v1) ←── 流量          blue (v1)              blue (v1) 保留待回滚
green(v2) 启动+验证    →     green(v2) ←── 流量  →  green(v2) ←── 流量
```

## 二、架构：流量开关是必需品

蓝绿的前提是有一个能改变流量去向的东西。本次用 nginx 反向代理。

```text
外部唯一入口 127.0.0.1:29080
        ↓
   d20-nginx（流量开关，只有它映射端口）
        ↓ proxy_pass
   d20-blue  (ci-web:v1)   ← 不映射端口
   d20-green (ci-web:v2)   ← 不映射端口
```

蓝绿容器**不对外映射端口**，只能通过内部网络访问。这样外部无法绕过网关直连某一个版本。

## 三、前置坑：默认 bridge 网络不解析容器名

nginx 要写 `proxy_pass http://d20-blue:8080`，依赖容器名 DNS 解析。实测对照：

```text
默认 bridge 网络：
  docker exec b ping -c1 a   →  ping: bad address 'a'

自定义网络 d20-net：
  docker exec b ping -c1 a   →  PING a (172.19.0.2): 56 data bytes
                                 64 bytes from 172.19.0.2: time=0.243 ms
```

**结论：容器名 DNS 解析只在自定义网络里可用**，默认 `bridge` 没有。所以必须先 `docker network create`。

### 顺带踩到的脚本问题

我在验证脚本里写了：

```bash
docker exec dnstest-b ping -c1 -W2 dnstest-a 2>&1 | head -3
echo "退出码: $?"      # ❌ 打印的是 head 的退出码，不是 docker exec 的
```

ping 明明失败了，却打印 `退出码: 0`。**管道会掩盖前面命令的失败状态**，`$?` 只反映最后一个命令。这正是 CI 脚本里要 `set -o pipefail` 的原因（Day 12 用过）。

## 四、重大坑：单文件挂载 + `sed -i` = 配置静默失效

第一次切换实验**完全失败**：222 个请求全部命中 blue，流量没切过去。但所有命令都"成功"了：

```text
sed -i 执行成功
docker exec nginx -t  →  syntax is ok / test is successful
docker exec nginx -s reload  →  signal process started
switch.sh 退出码: 0
```

### 定位过程

对比宿主机和容器内看到的文件：

```text
宿主机配置：proxy_pass http://d20-green:8080;   ← 已改
容器内配置：proxy_pass http://d20-blue:8080;    ← 没变

宿主机 inode: 954945
容器内 inode: 949125    ← 根本不是同一个文件
```

### 根因

`sed -i` **不是原地修改**。它写一个临时文件，再 `rename` 覆盖原路径，**产生新 inode**。而 `-v 文件:文件` 这种单文件挂载，Docker 绑定的是**挂载时那个 inode**：

```text
1. cat > 创建文件                → inode 949125，容器挂载绑定到它
2. sed -i 改文件                 → 宿主机路径指向新 inode 954945
                                   容器仍绑在 949125（已成孤儿）
3. 之后无论怎么改宿主机文件        → 容器永远看不到
```

**绑定一旦被破坏就是永久的。** 我当时想用 `cat >`（不换 inode）去验证推断，结果也无效——因为损坏已经发生，宿主机路径已不再指向被挂载的那个 inode。这个对照实验不足以证明任何事，必须重建容器重新测。

### 完整矩阵（重建容器后逐项验证）

| 挂载方式 | 修改方式 | 容器是否看到新配置 |
|---|---|---|
| 单文件 `-v f:f` | `cat >`（inode 不变） | ✅ 生效 |
| 单文件 `-v f:f` | `sed -i`（inode 改变） | ❌ **静默失效** |
| 目录 `-v dir:dir` | `sed -i` | ✅ 生效 |

⭐ **两个可用方案：**
1. **挂载目录而非单个文件**（推荐，对修改方式不敏感）
2. 坚持单文件挂载时，只用 `>` 重定向覆盖，不用 `sed -i` / `vim`（vim 默认也是写新文件再 rename）

⚠️ **这个坑最危险的地方是无任何报错。** 命令全部返回 0、`nginx -t` 通过、reload 正常，配置却没生效。排查时唯一可靠的手段是**进容器看它实际读到的内容**，而不是看宿主机文件。

## 五、核心测量：两种方式的停机时间

探测方法：每约 20ms 发一次请求，记录 `时间戳 状态码 命中后端`，中途执行切换，统计失败数。

后端识别靠 nginx 加响应头（应用本身没有版本接口）：

```nginx
add_header X-Backend "d20-blue" always;
```

> curl 7.81 不支持 `-w '%header{...}'`（需 7.83+），所以用 `curl -sSi` 拿完整响应再解析头。

### 蓝绿切换（目录挂载修好之后）

```text
总请求: 222   成功: 222   失败: 0
后端分布:  82 d20-blue / 140 d20-green

切换命令窗口: 819.710 → 819.906  (196ms)
最后一个 blue:  819.965
第一个 green:   820.014
间隔: 49ms   ← 等于探测间隔本身，不是停机
```

**零失败。**

值得注意的细节：reload 命令在 `819.906` 已返回，但 blue 一直服务到 `819.965`。这是 nginx 的**优雅重载**——老 worker 把手上请求处理完才退出，不掐断连接。

### 原地替换（Day 19 方式）对照

```text
[011.154] docker rm -f 开始
[011.762] 旧容器已删
[012.378] docker run 返回

总请求: 275   成功: 216   失败: 59
失败率: 21.5%
状态码分布: 59 个 000 / 216 个 200

首个失败: 011.229
末个失败: 014.718
不可用时长: 3.489 秒
```

`000` 是 curl 的「连不上」。空窗期内**所有请求全失败**。

### 结论对比

| 指标 | 蓝绿切换 | 原地替换 |
|---|---|---|
| 失败请求 | **0** | 59 |
| 失败率 | **0%** | 21.5% |
| 不可用时长 | **0** | **3.489 秒** |

注意不可用时长（3.489s）**长于** `docker rm` + `docker run` 的命令耗时（1.2s）。因为 `docker run` 返回只代表容器已创建，**应用进程还要启动、绑定端口**，这段时间端口上依然没人监听。

⭐ **面试要点：`docker run` 返回成功 ≠ 服务可用。** 必须用健康检查确认，不能用命令退出码判断。

## 六、回滚：从数秒变成毫秒

蓝绿回滚只是把流量切回去，**旧容器一直在跑**（实测 `Up 14 minutes`）。

```text
回滚耗时: 0.191 秒
总请求: 183   成功: 183   失败: 0
后端分布: 119 d20-blue / 64 d20-green

交界处:
  153.058 200 d20-green
  153.105 200 d20-blue    ← 47ms 内完成切换，无失败
```

对比 Day 19 的回滚：删容器 → 起旧镜像容器 → 等健康检查，数秒不可用。

| | 蓝绿回滚 | Day 19 回滚 |
|---|---|---|
| 耗时 | 0.191 秒 | 数秒 |
| 失败请求 | 0 | 有 |
| 依赖 | 旧容器还在 | 旧镜像还在 |

## 七、最重要的安全属性：坏版本拿不到流量

这才是蓝绿的核心价值，不只是"快"。用 Day 19 那个有缺陷的 v3 验证（缺 `APP_GREETING` 则进程退出）：

```text
1. green 换成坏版本
   green 状态: Exited (1) 1 second ago
   green 日志: ERROR: APP_GREETING is required

2. 切流前的强制验证（闸门）
   验证失败 -> 拒绝切换

3. 未执行切换，流量保持在 blue

4. 核实线上服务
   请求1-5: HTTP/1.1 200 OK   X-Backend: d20-blue
```

闸门的实现是从内部网络去验证 green，**在切流之前**：

```bash
if docker run --rm --network d20-net curlimages/curl:latest \
     -fsS --max-time 5 http://d20-green:8080/healthz >/dev/null 2>&1; then
  ALLOW=yes
else
  ALLOW=no    # 拒绝切换
fi
```

**同一个坏版本，两种方式的结果：**

| | 蓝绿 | Day 19 原地替换 |
|---|---|---|
| 线上影响 | **零** | 3.5 秒以上不可用 |
| 是否需要回滚 | 不需要（压根没切） | 需要 |
| 用户是否感知 | 否 | 是 |

⭐ 本质区别：**原地替换是"先破坏现状再验证"，蓝绿是"先验证再切换"。**

## 八、代价：资源翻倍

```text
d20-blue    18.75MiB / 96MiB   0.01%
d20-green   23.48MiB / 96MiB   0.01%
d20-nginx    8.297MiB / 64MiB  0.00%

整机: total 1608  used 884  available 539
```

| 代价 | 说明 |
|---|---|
| 内存/CPU | 两份应用常驻，约翻倍 |
| 多一个组件 | 网关自身成为单点，需要考虑它的高可用 |
| 运维复杂度 | 要记住当前哪个是活动色，避免切错 |
| 数据层 | **本次未涉及**：两版本共用数据库时，schema 变更必须向后兼容 |

**对 To B 交付的意义：** 客户机器资源有限时，蓝绿的内存开销要先算清楚。本次应用只占 ~20MiB，翻倍无压力；若是占几 G 的服务，就得评估是否改用滚动更新（逐个替换，牺牲部分可用性换资源）。

## 九、三种发布方式的取舍

| 方式 | 停机 | 资源 | 回滚速度 | 适用 |
|---|---|---|---|---|
| 原地替换 | 有（秒级） | 1x | 慢 | 内部系统、允许短暂中断 |
| 蓝绿 | 无 | 2x | 极快 | 不允许中断、资源充足 |
| 滚动更新 | 无（容量下降） | 1x + 1 | 中等 | 多实例、资源受限 |

> 滚动更新本次未实验，上表该行为推断，未验证。

## 十、面试答法

> **问：怎么做到不停机发布？**
> 关键是把「验证」提到「切流」之前。原地替换是先删掉正在服务的容器再起新的，中间端口上没人监听，实测有 3.5 秒完全不可用、21.5% 请求失败。蓝绿是新版本在旁边起好、从内网验证通过后，才把网关的后端指向它，实测 222 个请求零失败。
>
> 两个额外收益：一是回滚变成改一次网关配置，实测 0.19 秒，因为旧容器一直在跑；二是坏版本根本拿不到流量——我用一个启动即退出的镜像验证过，切流前的健康检查不通过就终止切换，线上完全无感知。
>
> 代价是资源翻倍和多一个网关组件。另外数据层不能忽略：两个版本若共用数据库，schema 变更必须向后兼容，否则蓝绿等于把两套不兼容的代码同时对着一份数据。

## 十一、本次未覆盖

- 金丝雀/灰度：按权重或按用户分流（nginx `upstream` + `weight`）
- 跨机器蓝绿（本次两套在同一台机器）
- 滚动更新实测对比
- 数据库 schema 向后兼容的具体做法
- 网关自身的高可用（当前 nginx 是单点）
- 长连接/WebSocket 场景下的切换行为（本次只测短连接 HTTP）
- 把蓝绿接进 Ansible / CI 自动执行（当前为手工脚本）
