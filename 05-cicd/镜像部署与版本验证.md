# 已发布镜像的部署与版本验证

> Day 15，2026-10-28。目标机：阿里云 ECS（Ubuntu 22.04，x86_64）。
> 本次是**手动部署**，没有配置 Actions 远程 SSH；Mac 只做编辑与 Git，部署命令在 ECS 执行。
> 输出为用户实际终端结果；未采集项明确标注。

## 一、部署不是重新构建

目标机器拉取已验证的镜像，而不是拿源码重新 build：

- 避免构建环境差异导致产物不一致。
- 让线上版本能对应到一次发布结果。
- 有明确的回滚目标。

```text
GitHub runner：构建 → 冒烟验证 → 推送 GHCR
                                    ↓
ECS：按 digest 拉取 → 启动 → 验证版本/HTTP/身份
```

本次部署使用 Day 14 采集的 digest：

```text
ghcr.io/xuxiaojing-cq/ci-web@sha256:0416a982d2b06591679d9d18d830e09c51815c11b8b69e316db31f1633b8e085
```

**面试答法：** 构建一次，把同一产物交付到目标环境。提交 SHA 标签用于追溯源码，digest 用于固定镜像内容，避免标签被覆盖后拉到不同版本。

## 三、拉取与镜像信息

```bash
mkdir -p ~/day15

IMAGE='ghcr.io/xuxiaojing-cq/ci-web@sha256:0416a982d2b06591679d9d18d830e09c51815c11b8b69e316db31f1633b8e085'

```

实测：

```text

```

### 平台与 digest

```bash
docker image inspect "$IMAGE" \
  --format 'ID={{.Id}} OS={{.Os}} Architecture={{.Architecture}}'
docker image inspect "$IMAGE" --format '{{json .RepoDigests}}'
```

```text
ID=sha256:0416a982d2b06591679d9d18d830e09c51815c11b8b69e316db31f1633b8e085 OS=linux Architecture=amd64
["ghcr.io/xuxiaojing-cq/ci-web@sha256:0416a982d2b06591679d9d18d830e09c51815c11b8b69e316db31f1633b8e085"]
```

`linux/amd64` 与 ECS 的 `x86_64` 匹配。架构不匹配时，镜像能拉下来也未必能运行。

### 一个需要准确表述的细节

本次 **镜像 ID 与 registry digest 完全相同**。这不是普遍规律：Docker 29 使用 containerd 镜像存储，镜像 ID 取 manifest digest；经典 overlayfs 存储的镜像 ID 通常取配置 digest，两者会不同。

所以不能笼统地说“镜像 ID 一定等于 digest”或“一定不等”，应说明它取决于镜像存储后端。判断部署版本时，比较运行容器的 `.Image` 与目标镜像 ID，或直接用 digest 引用。

## 四、启动容器的约束

```bash
docker run -d \
  --name day15-ci-web \
  --restart unless-stopped \
  --memory 128m \
  --cpus 0.25 \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  -p 127.0.0.1:18080:8080 \
  "$IMAGE"
```

| 参数 | 作用 |
|---|---|
| `--restart unless-stopped` | 非人为退出时自动恢复；主动停机后不自己起来 |
| `--memory 128m` | 内存上限 |
| `--cpus 0.25` | CPU 使用限制 |
| `--log-opt` | 限制日志大小与文件数，避免无限增长 |
| `127.0.0.1:18080:8080` | 只在 ECS 回环提供访问，不直接暴露公网 |

**这些资源值是教学保护值，不是生产容量建议。** 真实应用要按测量结果设置，并且注意：设置内存上限后，超限可能被 OOM 终止，需要配合监控。

## 五、验证部署：四层证据

只看 Up 不够。实测结果：

### 1. 容器状态与启动日志

```text
day15-ci-web   Up   127.0.0.1:18080->8080/tcp
Listening on port 8080
```

日志只说明端口，**不包含绑定地址**，不能仅凭它判断外部可达（Day 13 的回环绑定故障就是这么发生的）。

### 2. HTTP 状态与正文

```bash
curl --fail --show-error --silent --max-time 5 http://127.0.0.1:18080/healthz
```

```text
ok
```

`--fail` 让 4xx/5xx 返回非零退出码，避免“收到错误页但命令成功”。

### 3. 运行身份

```bash
docker exec day15-ci-web id
```

```text
uid=10001 gid=10001 groups=10001
```

### 4. 运行版本与目标镜像一致

```bash
EXPECTED_ID=$(docker image inspect "$IMAGE" --format '{{.Id}}')
RUNNING_ID=$(docker inspect day15-ci-web --format '{{.Image}}')
test "$EXPECTED_ID" = "$RUNNING_ID" && printf 'PASS: image ID matches\n'
```

```text
PASS: image ID matches
```

这里比较的是两个镜像 ID；容器名可以重复使用，名字相同不代表镜像相同。

## 六、访问边界

容器绑定在 ECS 回环，公网无法直连。远程验证走 SSH 隧道：

```bash
# Mac，保持前台运行
ssh -N -L 18080:127.0.0.1:18080 myecs
```

```bash
# Mac 另一个终端
curl -i --max-time 5 http://127.0.0.1:18080/healthz
```

实测：

```text
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.16
Content-Type: text/plain
Content-Length: 3

ok
```

调用链：

```text
Mac 127.0.0.1:18080 → SSH 隧道 → ECS 127.0.0.1:18080 → 容器 :8080
```

**没有开放公网端口，没有修改安全组。**

两个备注：

- 响应用 `HTTP/1.0`，是 Python `BaseHTTPRequestHandler` 的默认行为，不是生产 HTTP 服务的最佳实践。
- 若 SSH 主机别名里已配置了其他 `LocalForward`（本次 Mac 上 3000、9090 已存在占用），会出现端口占用的提示；那是本地端口冲突，与本次 18080 转发和验证结论无关。用完记得 `Ctrl + C` 关闭隧道。

## 七、部署记录

```bash
{
  echo "deploy_time=$(date -Is)"
  echo "image=$(<image-ref.txt)"
  echo "image_id=$(docker inspect day15-ci-web --format '{{.Image}}')"
  echo "container_id=$(docker inspect day15-ci-web --format '{{.Id}}')"
  echo "platform=$(docker image inspect "$IMAGE" --format '{{.Os}}/{{.Architecture}}')"
  echo "health=$(curl -fsS --max-time 5 http://127.0.0.1:18080/healthz)"
  echo "runtime_uid=$(docker exec day15-ci-web id -u)"
} | tee deployment-record.txt
```

实际内容：

```text
deploy_time=2026-10-28T21:09:23+08:00
image=ghcr.io/xuxiaojing-cq/ci-web@sha256:0416a982d2b06591679d9d18d830e09c51815c11b8b69e316db31f1633b8e085

container_id=1b03365ceffa222553fef053fe453f670288757e879365a20309ddfa1344b3cb
platform=linux/amd64

```

这份记录的价值：**回滚时能确认要恢复到的确切版本**，排查时能知道当时部署的是哪一个镜像。

## 八、健康检查的边界与面试速记

`/healthz` 返回固定 `ok`，没有检查真实依赖。生产探针要反映关键依赖状态，但不能把所有外部依赖都塞进去，否则依赖抖动会让服务整体被判死。

**面试答法：** 部署完成不等于服务可用。要分层验证——容器运行、HTTP 状态与正文、运行身份、实际镜像版本一致；并记录部署版本与时间，作为回滚依据。未认证的服务不应直接绑定 `0.0.0.0` 暴露公网，调试用 SSH 隧道，对外应经过带认证与 TLS 的反向代理并限制来源。
