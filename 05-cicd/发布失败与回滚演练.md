## 一、回滚要成立，需要先有这四样

| 前提 | 本次情况 |
|---|---|
| 镜像有不可变标识 | 有 digest |
| 旧版本仍可拉取 | GHCR 上的 `sha256:0416a9...` 仍在 |
| 记录了旧版本的部署参数 | Day 15 的 `deployment-record.txt` |
| 验证方式可复用 | HTTP + 运行身份 + 镜像 ID 一致性 |

**回滚不等于“找个旧文件重新跑一下”，而是按记录恢复到确切的旧版本。** 没有部署记录，就只能靠记忆重建启动命令。

## 二、故障设计：让 CI 通过，让目标环境失败

如果 CI 能拦下问题，就没有回滚可练。因此本次构造的故障必须**在 CI 环境可用、在目标环境不可用**。

做法是只增加一个运行时必需条件，不改健康检查路径：

```python
if __name__ == "__main__":
    greeting = os.environ.get("APP_GREETING")
    if not greeting:
        print("ERROR: APP_GREETING is required", file=sys.stderr, flush=True)
        sys.exit(1)
```

CI 的启动命令补充变量：

```yaml
docker run -d \
  --name day13-ci-web \
  -e APP_GREETING=ci-demo \
  ...
```

于是形成错配：

```text
CI 的 docker run      传了 APP_GREETING → 冒烟测试成功 → 镜像发布
ECS 的部署命令        没传             → 启动即退出 → 服务不可用
```

`/healthz` 响应保持不变，所以健康检查本身在 CI 里仍会通过——故障不体现在探针上，只体现在启动阶段。

### 一个顺带踩到的坑

第一次推送没有触发 Actions，因为 `on.push.branches` 里没有 `ci/day16-rollback-drill`，只匹配了前几天的分支名。补上后重新推送才运行。

**补充规则的那次推送自己就生效了**：GitHub 判断是否触发，读的是被推送提交里的 workflow 文件。

## 三、实测：CI 绿，部署挂

### CI 侧（分支提交 `073699c`）

```text
check-markdown  ✅
docker-smoke    ✅    ← CI 传了变量，启动成功
Log in / Publish / Log out  Skipped   ← 普通推送不发布
```

### 发布 v2（main，`6e3279a`）

```text
tag:    ghcr.io/xuxiaojing-cq/ci-web:sha-6e3279a6864ef7988c68983227e52fe6ed44f19e
digest: sha256:32dec93da45d4d4987952cd136af80f0840ceaf362c50a1bc5e4d1cc57ffe4a0
```

推送前后用只读 manifest 查询验证过：tag 与 digest 均返回 HTTP 200，指向同一镜像。

### ECS 侧部署失败

```text
docker ps          Up Less than a second        ← 恰好抓住刚起来的瞬间
docker ps -a       Restarting (1) 19 seconds ago
docker logs        ERROR: APP_GREETING is required（连续 11 条）
Status=restarting  ExitCode=1  Restarts=11 → 12
curl 18081         Failed to connect ... Connection refused（exit=7）
curl 18080         ok                            ← 基准版本未受影响
```

三个细节值得记住：

1. **`docker ps` 不一定为空。** 带 `--restart` 的容器处于 `Restarting` 时不是终态，仍可能短暂显示为 `Up Less than a second`。我事先预判“大概是空的”，实测推翻了。
2. **`ExitCode=1` 是程序主动退出**；若被内存限制杀死通常是 137（Day 8 的结论）。用退出码可以区分失败类型。
3. **`Restarts` 11 → 12 用了约一分钟**，与 Docker 重启退避、逐步拉长间隔、接近上限就稳定在约 60 秒一次的行为相符。未逐次采集时间戳，只作为一致性判断。

⭐ 这就是 Docker 版的 `CrashLoopBackOff`：能启动、立刻退出、按退避重试。

## 四、真实回滚：制造服务中断再恢复

前一步只是“另一个端口上的失败版本”，基准服务没断。真正的回滚演练要模拟替换：

```text
docker stop day15-ci-web              → 18080 refused（exit=7），服务真中断
用错误配方在 18080 起 v2              → Still Restarting，仍不可用
docker rm -f day16-ci-web             → 清掉失败容器
docker start day15-ci-web             → 恢复 v1
```

### 两种回滚路径

| 路径 | 适用 | 命令 |
|---|---|---|
| A：启动已有旧容器 | 旧容器还没删 | `docker start <旧容器名>` |
| B：按记录重建 | 旧容器已被删（生产常态） | 用旧 digest 重新 `docker run` |

**本次走的是 A，但 B 才是生产里更常见的情况。** 这也是 `deployment-record.txt` 的价值：它保留的镜像引用和启动参数，正是路径 B 需要的东西。

路径 A 更快，但隐含一个风险：旧容器的配置可能早已和预期不一致（有人手动改过、挂载丢失）。**能重建就不要只 stop/start**，除非时间确实紧张。

### 回滚后验证（实测）

```text
docker ps             Up  127.0.0.1:18080->8080/tcp
curl 18080/healthz    ok
docker exec id        uid=10001 gid=10001
镜像 ID 对比           PASS: image ID matches
```

我又用只读命令做了独立核实：

```text
day15-ci-web   Up  127.0.0.1:18080->8080/tcp
18080 监听      docker-proxy
18080 health    http_code=200
day16-ci-web    不存在
```

**为什么要单独核实：** 用户提交的输出里省略了 `docker rm -f` 和 `docker start` 两条命令，不能凭记录假定回滚真的发生。核实后才确认容器状态确实恢复。

## 五、一个容易误判的验证点

```text
docker inspect day15-ci-web --format '{{.Image}}'
```

对**已停止**的容器同样能返回镜像 ID。因此：

```text
PASS: image ID matches
```

只证明“这个容器的配置指向 v1”，**不能证明它在运行**。

真正的恢复证据是 `health=ok` 与端口监听状态。

**版本正确** 和 **服务活着** 是两条独立的检查，缺一条都可能漏判：

- 只查版本：容器停在 Exited，也会显示 PASS。
- 只查健康：新镜像也返回 200，但跑的不是你以为的版本。

## 六、根因确认：镜像没问题，是部署配方错了

回滚后用同一份 v2 镜像、在另一个端口、这次带上变量再跑一次：

```bash
docker run -d --name day16-fix-check \
  -e APP_GREETING=verify-fix \
  -p 127.0.0.1:18082:8080 \
  "$IMAGE_V2"

curl -fsS --max-time 5 http://127.0.0.1:18082/healthz
```

实测：

```text
ok
```

**镜像本身可正常运行。** 失败的唯一差异是启动时缺少环境变量。

这一步把根因从推断变成了实测——如果没有这一步，“配置漂移”只是从现象倒推的假设。

### 面试答法

> CI 通过只证明它在 CI 的运行环境里可用。CI 与目标环境的启动参数、环境变量、端口和外部依赖必须保持一致，否则会出现“流水线全绿、上线即挂”。这类问题靠部署后验证发现；确认镜像本身无缺陷后，修复方向是对齐部署配置而非回滚长期停留。

## 七、回滚记录与 MTTR 的诚实表述

```text
rollback_time=2026-10-29T21:34:00+08:00
failed_image=ghcr.io/.../ci-web@sha256:32dec9...
failed_exit_code=1
failed_reason=APP_GREETING is required
restored_image=ghcr.io/.../ci-web@sha256:0416a9...
restored_image_id=sha256:0416a9...
health=ok
runtime_uid=10001
```

失败记录（21:18）到回滚记录（21:34）约 **15 分钟**。

**这只是演练耗时，不是可引用的生产 MTTR。** 这段时间包含指令生成、人工阅读和执行，不能外推为“团队 15 分钟内可恢复”。

要得到有意义的 MTTR，需要固定操作步骤、明确判定权限，并统计多次演练；单次人工演练不足以下结论。

## 八、这次演练还没覆盖的

- 回滚后**数据状态**未验证：本次服务无状态，若涉及数据库结构变更，回滚可能造成更严重后果。
- 未演练**部分实例失败**：多副本滚动发布中只有部分新实例不健康时，判断和处置方式不同。
- 未演练**回滚本身失败**：旧镜像拉取失败、端口仍被占用、旧容器配置漂移，都需要预案。
- 未设计**自动回滚**：监控指标不达标时自动切回旧版本，涉及判定阈值与误报风险。
- 未设定**发布后的观察窗口**：多久没有异常才算发布成功，本次没有定义。

**面试答法：** 回滚能力来自四件事——不可变镜像标识、可拉取的旧版本、可复现的部署记录、可复用的验证方式。缺任何一项，回滚就会退化成临场重建。

## 九、本次实验修正的认知

| 原以为 | 实测 |
|---|---|
| 带 `--restart` 的崩溃容器不会出现在 `docker ps` | 会短暂显示 `Up Less than a second`，`Restarting` 不是终态 |
| 镜像 ID 一致就说明回滚成功 | 只说明配置指向旧镜像；服务是否恢复要看端口与健康检查 |
| CI 通过就能代表部署可用 | 只在 CI 的运行配方下成立；环境变量不同结果就不同 |
| 分支推送一定会触发 CI | 必须在该 workflow 的 `on.push.branches` 列表内 |
