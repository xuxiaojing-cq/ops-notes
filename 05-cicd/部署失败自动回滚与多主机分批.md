# 部署失败自动回滚与多主机分批交付

> Day 19，2026-11-05。控制节点为 Mac（Ansible core 2.18.19，虚拟环境 `~/.venvs/ansible`），目标为一台 ECS。
> ⚠️ 环境限制如实说明：只有一台真实服务器，所以「多主机」用**同机三实例**模拟——三个 inventory 主机名指向同一 IP，各自独立的容器名与端口。它能验证分批、失败中断、单机回滚的逻辑，**不能验证真实网络与硬件差异**。
> 所有输出为实际执行结果；未验证项明确标注。

## 一、要解决的问题

Day 18 做到了「CI 验证 → 发布 → 人工批准 → 自动部署」。但部署失败之后呢？

```text
Day 16 回滚：人工发现 → 人工查记录 → 人工敲命令 → 人工验证
Day 19 回滚：健康检查失败 → playbook 自动还原上一版 → 自动验证 → 仍然报错
```

两个诉求：

| 诉求 | 做法 |
|---|---|
| 单机失败要能自愈 | `block` / `rescue` 包住部署，失败时还原回滚点 |
| 一批机器里少数失败不能让全部回滚 | `serial` 分批 + 批内独立回滚 |

## 二、自动回滚的前提：回滚点必须是"读出来的"

最容易犯的错误是**把回滚目标写死在变量里**。写死意味着回滚到你以为的版本，不是实际在跑的版本。

```bash
docker inspect --format '{{.Image}}'    <容器>   # 记镜像 ID
docker inspect --format '{{json .Config.Env}}' <容器>  # 记环境变量
```

```yaml
- name: Decide rollback target
  ansible.builtin.set_fact:
    rollback_image: >-
      {{ (current_container.stdout | trim)
         if current_container.rc == 0 and (current_container.stdout | trim) | length > 0
         else fallback_image }}
    rollback_greeting: >-
      {{ ((current_env.stdout | from_json) | select('match', '^APP_GREETING=')
          | map('regex_replace', '^APP_GREETING=', '') | list | first | default('rollback'))
         if current_env.rc == 0 else 'rollback' }}
```

要点：

- `docker inspect` 对不存在的容器返回非零 → `failed_when: false` 让它变成"可判断的条件"，而不是直接中断
- **只记镜像不够，必须记环境变量**。镜像相同但 `APP_GREETING` 丢了，容器照样起不来
- 容器不存在时才用 `fallback_image` 兜底

实测输出（v1 → v2 升级时）：

```text
"container_existed": true,
"rollback_greeting": "baseline-v1",
"rollback_image": "sha256:0416a982d2b0...",
```

## 三、结构：block / rescue / always

```yaml
- name: Deploy and verify
  block:
    - 删除旧容器（仅当镜像不同）
    - 启动新容器
    - 等待 /healthz
    - 断言 health == "ok"
    - 断言运行用户是 10001

  rescue:
    - 记录失败任务（ansible_failed_task.name）
    - 删除失败容器
    - block:  启动回滚容器 → 验证 /healthz → 标记还原成功
      rescue: 标记"回滚失败，需人工介入"

    - fail: 即便回滚成功，也要让这台机器报失败
```

### 关键设计：`rescue` 之后必须再 `fail`

Ansible 的 `rescue` 语义是"错误已被处理"，任务默认会记为 **ok**。但**回滚成功 ≠ 部署成功**——如果流水线显示绿色，人就不会去看。

```yaml
- name: Fail the host even when rollback worked
  ansible.builtin.fail:
    msg: >-
      deploy of {{ app_image }} failed on {{ inventory_hostname }};
      {{ rollback_result }}
```

实测 RECAP 同时出现两个数字：

```text
web01 : ok=16  changed=4  failed=1  rescued=1
```

`rescued=1` 说明 rescue 分支跑过了，`failed=1` 说明这台机器最终判定为失败。**两个都要有。**

### 嵌套 rescue：回滚也可能失败

回滚本身失败是最危险的情况——旧版本已经删了，新版本起不来，机器上什么都没有。所以回滚块内部再套一层 `rescue`：

```yaml
- name: Restore previous version
  block:
    - 启动回滚容器
    - 验证 /healthz
    - set_fact: rollback_result = "restored ..."
  rescue:
    - set_fact: rollback_result = "rollback failed, manual intervention required"
```

## 四、实测：三种失败路径

准备三份镜像（同一应用的三个构建，用 `docker tag` 起可读名，不重新构建）：

```text
ci-web:v1 → sha256:0416a982d2b0...
ci-web:v2 → sha256:24d9bf0ec50f...
ci-web:v3 → sha256:1bda30a59939...
```

失败是**真实触发**的，不是伪造：`app.py` 在 `APP_GREETING` 为空时直接 `sys.exit(1)`，容器启动即退出，`/healthz` 连接被拒。

### 路径 A：有旧容器 → 失败 → 回滚到旧镜像

```text
TASK [Wait for health endpoint]
fatal: [web01]: FAILED! => {"attempts": 10, "msg": "Status code was -1 and not [200]:
  Request failed: <urlopen error [Errno 111] Connection refused>"}

TASK [Deployment failed, recording the cause]
  "failed_task": "Wait for health endpoint",
  "rollback_image": "sha256:24d9bf0e..."

TASK [Start rollback container]                        changed
TASK [Verify rollback is actually serving]             ok
TASK [Fail the host even when rollback worked]
fatal: deploy of ci-web:v3 failed on web01; restored sha256:24d9bf0e...

PLAY RECAP
web01 : ok=16  changed=4  failed=1  rescued=1
```

独立核实（不走 Ansible，直接 curl + inspect）：

```text
28081  ok
d19-web-01  Up 2 minutes  24d9bf0ec50f      ← 镜像确实回到 v2

d19-web-01  img=sha256:24d9bf0e...  env=["APP_GREETING=upgraded-v2", ...]
```

**环境变量也还原了**，不只是镜像。

### 路径 B：全新机器（无旧容器）→ 失败 → 用兜底镜像回滚

先把容器删掉，模拟一台从未部署过的机器：

```text
"container_existed": false,
"rollback_image": "ci-web:v2",       ← 走了 fallback_image
"rollback_greeting": "rollback"
...
fatal: deploy of ci-web:v3 failed on web03; restored ci-web:v2
```

结果：容器起来了、健康、但**这次本来就不该有"上一版"**，所以回滚等于"起了个默认版本"，本质上仍是部署失败。

### 路径 C：回滚也失败 → 必须显式喊出来

把 `fallback_image` 指向不存在的名字，让回滚的 `docker run` 直接失败：

```text
TASK [Start rollback container]
fatal: [web03]: FAILED! => {"rc": 125, "stderr": "Unable to find image
  'ci-web:doesnotexist' locally\ndocker: Error response from daemon: ..."}

TASK [Rollback itself failed]                          ok
TASK [Fail the host even when rollback worked]
fatal: deploy of ci-web:v3 failed on web03; rollback failed, manual intervention required

PLAY RECAP
web03 : ok=13  changed=2  failed=1  rescued=2
```

`rescued=2` 证明**两层 rescue 都执行了**。最终状态核实：

```text
docker ps -a --filter name=d19-web-03   → 空
curl http://127.0.0.1:28083/healthz     → Connection refused
```

**机器上没有任何容器。** 这是真实事故里最需要立刻告警的状态，而 `fail` 消息里已经写明了。

## 五、多主机：serial 与 max_fail_percentage

```yaml
- hosts: web
  serial: "{{ batch_size | default(1) }}"
  max_fail_percentage: "{{ max_fail_pct | default(0) }}"
```

### 实验：A/B/C 三组对照

目标：web01 + web02，两台都注定失败（`app_greeting=` 为空）。

| 组 | 参数 | 实际执行的主机 | 结论 |
|---|---|---|---|
| A | `batch_size=1`（默认）, `max_fail_pct=0` | 只有 web01 | 当前批全失败 → 停止后续 |
| B | `batch_size=1`, `max_fail_pct=100` | 只有 web01 | **`max_fail_percentage` 没起作用** |
| C | `batch_size=2`, `max_fail_pct=100` | web01 + web02 | 同批内每台独立回滚 |

A 组 RECAP 只有 web01，web02 根本不在里面，并出现 `NO MORE HOSTS LEFT`。

### 为什么 B 组 100% 也没继续

这是本次最值得记的一条。原因是 **`serial: 1` 每批只有 1 台**：

```text
批 1 的规模 = 1 台，失败 1 台 → 该批失败率 = 100% > max_fail_percentage
```

Ansible 在**批次粒度**上判断是否继续。`max_fail_percentage: 100` 也救不了，因为 100 不代表"无限容忍"——判断条件是 `失败率 > 阈值`，100 > 100 为假，理论上该继续，但实际仍停在批 1。

⭐ **准确结论（已验证部分）：** `serial: 1` 时每批 1 台，单台失败即整批失败，后续批不再执行；把这批扩大到 2 台后（C 组），两台都被执行，`max_fail_pct` 的容错才生效。

⚠️ **未能验证的推测**：Ansible 对"当前批全部失败"是否有独立的短路规则，本次实验不足以区分，未查阅文档确认，不写入结论。要确认需读 `ansible-playbook` 的 strategy 文档或逐台增加批大小复现。

### 对交付的实际意义

| 场景 | 建议 |
|---|---|
| 数百家机构批量升级 | `serial` 取小批量（如 5% 或固定 10 台），先观察一批再继续 |
| 少数失败不应拖停全局 | 提高 `max_fail_percentage`，但要配套告警 |
| 一旦有失败就必须人工介入 | 保持 `max_fail_percentage: 0` + `any_errors_fatal` |

**核心取舍：** 分批的价值不是"更快"，而是**把故障影响面限制在一批之内**。100 台一起推，全挂；分 10 批推，最多挂 10 台。

## 六、踩到的问题

### 1. playbook 一开始不幂等

初版「删除旧容器」的条件只判断了容器是否存在，没判断镜像是否相同：

```yaml
when: current_container.rc == 0      # ❌ 同版本再跑也会删掉重建
```

修复：

```yaml
- name: Record expected image ID
  set_fact:
    needs_recreate: >-
      {{ current_container.rc != 0
         or (current_container.stdout | trim) != (target_image.stdout | trim) }}
```

改完之后重复部署 v1 实测：

```text
web01/02/03 : ok=15  changed=0  skipped=3
```

**这类 bug 在手工测试时很容易漏掉**——只要每次都换镜像，就永远看不出问题。

### 2. 我设计的一次失败实验没测到目标分支

想测「回滚失败」，却用了一个 playbook 里根本不存在的变量 `rollback_greeting_override`。结果变量被忽略，回滚照常成功，输出 `restored sha256:24d9bf0e...`，**测试跑通了但什么都没证明**。

正确做法是构造真正能让回滚失败的输入：删掉容器 + 让 `fallback_image` 指向不存在的镜像。

⭐ 教训：验证失败路径时，必须确认"失败确实按预期方式发生了"再看结果，否则容易把"没走到那个分支"误读成"那个分支没问题"。

## 七、这套东西的边界

| 局限 | 说明 |
|---|---|
| 回滚 = 删旧容器再起新的 | 中间有**秒级不可用窗口**，不是零停机 |
| 回滚点只在本次执行内有效 | 如果上次部署本身就错了，回滚点也是错的 |
| 多主机是同机模拟 | 真实环境要处理网络分区、部分主机不可达、时钟/版本不一致 |
| 回滚验证只看 `/healthz` | 真实业务要加关键接口验证或冒烟用例 |
| 没有回滚频次限制 | 回滚后再失败可能无限循环，需要最大重试次数 |
| 未对接告警 | 失败目前只在 RECAP 里，需要推送到 IM/告警平台 |

## 八、面试答法

> **问：部署失败怎么处理？**
> 分三层。第一层是部署前先记录回滚点——从正在运行的容器里读镜像 ID 和环境变量，不是写死版本号。第二层是部署后用健康检查验证，失败则在 `rescue` 里还原回滚点并再次验证；回滚本身失败要单独捕获，明确报告"需要人工介入"。第三层是即便回滚成功，也要让这次执行报失败，因为回滚成功不等于发布成功，绿色的流水线会让人漏掉问题。
>
> 多机场景下用 `serial` 分批，把故障影响限制在一批之内。实测发现 `serial: 1` 时单台失败会导致后续批次不再执行，需要根据容忍度调整批大小和 `max_fail_percentage`。
>
> 局限要说清楚：这是"删掉旧的再起新的"，有秒级窗口，不是蓝绿部署；真要做到零停机需要流量切换机制。
