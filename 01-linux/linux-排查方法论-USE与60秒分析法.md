# Linux 排查方法论：USE 方法与 60 秒分析法

> 实践环境：Ubuntu 22.04.5 / 内核 5.15 / 2 vCPU / 1.6G 内存 / 无 Swap / 40G 云盘
> 日期：2026-09-08

## 一、为什么需要方法论

排查故障时最容易犯的错误，是凭直觉猜测原因、逐个尝试。
这种方式在简单问题上有效，遇到复杂问题就会陷入反复试错。

方法论的作用是提供一套**固定的检查顺序**，保证不遗漏、不跳跃，
每一步都用"通 / 不通"做二分，快速收敛范围。

## 二、USE 方法

对每一类资源，检查三个维度：

- **U — Utilization（使用率）**：资源被占用的时间比例
- **S — Saturation（饱和度）**：有多少工作在排队等待
- **E — Errors（错误）**：错误计数

### ⭐ 核心认知：使用率高 ≠ 有问题

真正的问题信号是 **Saturation** 和 **Errors**，不是 Utilization。

举例：
- CPU 100%、运行队列为 0 → 资源被充分利用，正常状态
- CPU 80%、运行队列远超核数 → 有任务在排队，存在瓶颈
- 磁盘 %util 100%、await 很低 → 请求连续但处理很快，不是瓶颈
- 磁盘 %util 100%、await 升高、队列增长 → 真正的 IO 瓶颈

这个区分决定了处置方向是否正确。

### USE 检查表

| 资源 | 使用率 | 饱和度 | 错误 |
|---|---|---|---|
| CPU | `top`、`mpstat -P ALL 1` | `uptime` 的 load、`vmstat` 的 r 列 | `dmesg` |
| 内存 | `free -h`、`vmstat` | `vmstat` 的 si/so | `dmesg -T \| grep -i oom` |
| 磁盘 IO | `iostat -xz 1` 的 %util | `iostat` 的 await、aqu-sz | `dmesg \| grep -i "i/o error"` |
| 磁盘容量 | `df -h` | 写入失败 | 应用日志 `No space left` |
| 磁盘 inode | `df -i` | 无法创建新文件 | 同上（易误判） |
| 网络 | `sar -n DEV 1` | `ss -s`、TCP 重传 | `sar -n EDEV 1` |
| 文件句柄 | `cat /proc/sys/fs/file-nr` | 接近 `ulimit -n` | `Too many open files` |

## 三、60 秒分析法

来源：Netflix《Linux Performance Analysis in 60,000 Milliseconds》

面对一台不熟悉的机器，用固定顺序的十条命令快速建立整体判断。

```bash
uptime         # 1. 负载趋势
dmesg -T | tail -20     # 2. 内核最近报错
vmstat 1 5              # 3. 整体资源概览
mpstat -P ALL 1 3     # 4. 各 CPU 核是否均衡
pidstat 1 3   # 5. 哪个进程在消耗
iostat -xz 1 3          # 6. 磁盘 IO
free -h   # 7. 内存
sar -n DEV 1 3   # 8. 网卡吞吐
sar -n TCP,ETCP 1 3  # 9. TCP 连接与重传
top   # 10. 综合确认
```

> 注：`iostat` / `mpstat` / `pidstat` / `sar` 由 `sysstat` 包提供，
> 最小化安装的系统默认没有，需 `apt install sysstat`。
> 生产排查时遇到"命令不存在"很常见，需要知道命令属于哪个包。

### ⭐ 分流逻辑：先看 vmstat 的 us / sy / wa / id

这是最快的分流依据：

| 观察 | 判断 | 下一步 |
|---|---|---|
| `us` 高 | 应用在做计算 | `pidstat` / `top` 定位进程，查代码逻辑、GC |
| `sy` 高 | 内核态开销大 | 查系统调用、上下文切换、中断 |
| `wa` 高 | 在等待 IO | 转 `iostat` 查磁盘，或查网络 |
| `id` 高但业务慢 | **不是资源瓶颈** | 查应用层：锁等待、外部依赖、DB 慢查询 |

最后一行尤其重要：资源指标全部正常但业务就是慢，
说明瓶颈不在这台机器的资源上，继续查资源是浪费时间。

## 四、vmstat 关键列详解

```
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 0  0   0 168348  68232 956820    0    0     0     0  967 1692  1  0 99  0  0
```

| 列 | 含义 | 异常信号 |
|---|---|---|
| **r** | 运行队列长度 | 持续 > CPU 核数 = CPU 饱和 |
| **b** | 阻塞进程数（等 IO，D 状态） | 持续 > 0 = IO 有问题 |
| si / so | swap 换入 / 换出 | 非 0 = 内存不足，严重影响性能 |
| in | 中断次数/秒 | 突增需排查 |
| **cs** | 上下文切换/秒 | 飙升 = 线程过多或锁竞争 |
| us / sy / id / wa | CPU 时间分布 | 见上方分流逻辑 |
| **st** | 被宿主机占用的 CPU 时间 | ⭐ 见下 |

### ⭐ st（steal time）—— 云环境特有指标

表示 vCPU 想执行但物理 CPU 被同宿主机其他租户占用的时间比例。

持续 > 10% 说明宿主机资源争抢严重。此时的典型现象是：
`us` 和 `sy` 都不高，看起来 CPU 很空闲，但业务响应变慢。

⚠️ 这种情况在自己的机器上做任何优化都无效，需要联系云厂商或迁移实例。
这是云环境排查与物理机的重要差异。

> 注意：`vmstat` 第一行是开机以来的平均值，不是当前值，读数时应跳过。

## 五、mpstat 的价值：发现单核瓶颈

`top` 显示的是所有核的平均值，会掩盖负载不均的问题。

```
CPU    %usr %sys   %idle
all    50.0   0.050.0      ← 看起来还有一半余量
  0   100.0 0.0     0.0    ← 实际 0 号核已打满
  1     0.0   0.0   100.0      ← 1 号核完全空闲
```

这种情况说明是**单线程瓶颈**，增加 CPU 核数无效，
需要改造程序为多进程/多线程，或水平扩展实例。

另外两列容易被忽略：
- `%soft`（软中断）：网络流量大时会升高，是网络处理瓶颈的信号
- `%irq`（硬中断）：设备中断频繁

## 六、iostat 关键列详解

```
Device   r/s   rkB/s  r_await   w/s   wkB/s  w_await  aqu-sz  %util
vda     0.30   7.67    2.19     0.49   9.82   1.97     0.00    0.09
```

| 列 | 含义 | 判断标准 |
|---|---|---|
| r/s、w/s | 每秒读写次数（IOPS） | 对比云盘规格上限 |
| rkB/s、wkB/s | 每秒读写吞吐 | 对比云盘带宽上限 |
| **r_await / w_await** | 平均等待时间（含排队） | > 20ms 需警惕 |
| **aqu-sz** | 平均队列长度 = 饱和度 | 持续 > 1 表示排队 |
| **%util** | 设备繁忙时间占比 | ⚠️ 不能单独作为判断依据 |

### ⚠️ %util 100% 不等于磁盘满负荷

现代 SSD 和云盘可以并行处理多个 IO 请求，
`%util` 仅表示"该时间段内有请求在处理"，不代表队列已满。

正确判断方式：
- %util 高 + await 低 + aqu-sz 低 → 请求连续但处理迅速，未饱和
- %util 高 + await 升高 + aqu-sz > 1 → 真正的 IO 瓶颈

这与 USE 方法中"使用率 ≠ 饱和度"是同一个逻辑。

> `-z` 参数会跳过零活动设备，可过滤掉大量 loop 设备的噪音。
> 同样地，第一次输出为累计平均值，应忽略。

## 七、load average 的两个特性

```
load average: 0.00, 0.01, 0.00      # 1分钟 / 5分钟 / 15分钟
```

判断基准是 **CPU 核数**：2 核机器上 load 持续 > 2 说明有任务排队。

### 特性一：Linux 的 load 包含等待 IO 的进程

与其他 Unix 不同，Linux 的 load average 统计的是
「运行中 + 可运行 + 不可中断睡眠（D 状态，通常在等 IO）」的进程数。

因此 **load 高不一定是 CPU 忙**，也可能是磁盘 IO 阻塞。
必须结合 `vmstat` 的 `wa` 列和 `iostat` 一起判断。

### ⚠️ 特性二：存在延迟，是指数移动平均

实测验证：启动 2 个 CPU 密集进程后，load 并非立即变为 2，
而是在数十秒内逐渐爬升；kill 之后也需要数分钟才降回。

由此得出两条实践结论：
1. 故障刚发生时 load 仍然很低，**不能因为 load 不高就排除 CPU 饱和**
2. 处置后 load 缓慢下降，**不能用 load 判断是否已恢复**

需要实时判断时，应使用 `vmstat` 的 `r` 列——它反映的是瞬时运行队列。

## 八、实测记录：CPU 饱和

制造方式：在 2 核机器上启动 2 个 CPU 密集型进程

```bash
for i in 1 2; do (while true; do :; done) & done
```

### 数据对比

| 指标 | 空闲基线 | CPU 打满 | 说明 |
|---|---|---|---|
| r | 0 | **2** | 运行队列等于核数，达到饱和临界 |
| b | 0 | 0 | 无 IO 阻塞 |
| us | 1 | **99-100** | 用户态打满 |
| sy | 0 | 0-1 | 内核态几乎无消耗 |
| id | 99 | **0** | 无空闲 |
| **wa** | 0 | **0** | ⭐ 关键观察，见下 |
| 各核 %usr | 1% | 两核均 99%+ | 调度均衡 |

### ⭐ 关键结论：wa 全程为 0

CPU 使用率 100% 的情况下，`%iowait` 始终为 0。

这验证了一个常被误解的概念：
**`%iowait` 不是"CPU 忙"，而是"CPU 空闲着，在等待 IO 返回"。**

因此：
- `us` 高 + `wa` 低 → CPU 确实在计算，扩容 CPU 有效
- `us` 低 + `wa` 高 → CPU 其实空闲，瓶颈在磁盘或网络，**加 CPU 无效**

生产环境中"服务变慢就加配置"之所以常常无效，
根源就在于没有区分这两列。

### us 高 vs sy 高 的含义

本次实验是纯计算循环，几乎不调用内核，所以 `us` 99% 而 `sy` 接近 0。

对应到真实场景：
- **us 高**：复杂算法、正则回溯、加解密运算、JVM 频繁 GC、死循环
- **sy 高**：大量系统调用、频繁创建销毁进程、网络收发包密集、上下文切换剧烈

## 九、清理与恢复验证

```bash
kill %1 %2
jobs      # 确认已清空
vmstat 1 3          # r 回到 0，id 回到 99
```

> 排查的完整闭环包含"确认已恢复"这一步。
> 注意此时 load average 仍会维持一段时间的高位，属正常现象。

## 十、方法论小结

1. **先定性，再动手**：用只读命令看清状态，再决定处置手段
2. **关注饱和度而非使用率**：排队才是问题，忙碌不是
3. **分流靠 us/sy/wa/id**：四个值决定往哪个方向深入
4. **注意指标的时间特性**：load 有延迟，vmstat 首行是累计值
