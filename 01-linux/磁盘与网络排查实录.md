# 磁盘与网络排查实录：四类典型故障的定位方法

> 实践环境：Ubuntu 22.04.5 / 2 vCPU / 1.6G 内存 / 40G 云盘
> 日期：2026-09-08
> 说明：均为在个人服务器上主动制造故障并完成定位的实测记录

## 一、磁盘空间"删了但没释放"

### 现象

删除大文件后，`df` 显示的可用空间没有增加，`du` 也统计不到该文件。

### 原理

Linux 中删除文件释放磁盘块，需要**同时**满足两个条件：

1. 硬链接数归零（`rm` 完成了这一步，移除的是目录项）
2. **没有任何进程持有该文件的打开句柄**

只要还有进程握着 fd，inode 就不会被回收，数据块继续占用空间。
表现为：文件名消失，但空间仍被占用。

### ⚠️ 实验设计中踩的两个坑

这部分比结论本身更有价值，记录下来。

**坑一：`>>` 无法复现该现象**

最初的实验脚本是：

```bash
while true; do echo "..." >> /tmp/test.log; done
```

这个脚本复现不了。原因是 `>>` 在每次循环时**重新打开并关闭文件**，
句柄不是持续持有的。`rm` 之后下一次循环会直接创建一个新文件。

正确做法是用 `exec` 打开一次 fd 并持续持有：

```bash
exec 9>/tmp/bigfile   # 打开一次，fd 9 持续持有
dd if=/dev/zero bs=1M count=2048 >&9
```

> ⭐ 这个差异解释了 logrotate 为什么需要 `copytruncate` 或
> 向进程发送 `SIGHUP`：真实服务在启动时打开日志文件后会一直持有 fd，
> 如果直接 `rm` 或 `mv` 掉日志文件，程序仍会向旧 fd 写入，
> 新建的日志文件永远是空的，而旧文件的空间也不会释放。

**坑二：`df -h` 精度不足，掩盖了变化**

写入几十 MB 后用 `df -h` 观察，显示始终是 `4.0G`，看不出任何变化。
原因是 `-h` 对 40G 的分区只精确到 0.1G（约 100MB）。

改用 `df -m`（MB）后，2GB 的变化清晰可见。

> ⭐ 引申：**"看起来没有变化"不等于"没有发生变化"**，
> 可能只是观测精度或采样粒度不够。
> 同理，监控图上的平直曲线也可能是采样间隔过大平滑掉了短时抖动。
> 排查时如果结论是"一切正常"，应先反问：是真的正常，还是观测手段看不到？

### 定位方法

```bash
lsof +L1      # 列出硬链接数 < 1 的文件，即已删除但仍被打开的

# 按占用体积排序，直接找到元凶
lsof +L1 | awk '{print $7, $1, $2, $NF}' | sort -rn | head -10
```

`+L1` 比 `lsof | grep deleted` 更好：精确匹配、速度更快、有 NLINK 列。

### 处置手段

| 方式 | 命令 | 适用场景 |
|---|---|---|
| 优雅 | `systemctl restart 服务名` | 允许短暂中断 |
| ⭐ 应急 | `> /proc/PID/fd/N` | **不中断服务，空间立即释放** |
| 根治 | 配置 logrotate | 长期方案 |

应急手段说明：`> /proc/PID/fd/N` 是清空文件内容，不是删除。
进程无感知继续写入，空间立刻归还。
⚠️ 此时不能用 `rm`——文件已经删过了，再删无效。

### ⭐ 附带发现：真实环境中的 deleted 文件

在服务器上执行 `lsof | grep deleted` 时，发现了系统自身的两类情况：

**类型一：`txt` 类型——程序二进制被替换**

```
tuned   778  root  txt  REG  252,3  5937704  /usr/bin/python3.10 (deleted)
agetty  799  root  txt  REG  252,3    56896  /usr/sbin/agetty (deleted)
```

`txt` 表示进程正在执行的程序文件本身。
系统更新（apt upgrade）替换了新版二进制，旧 inode 被标记删除，
但这些进程仍在运行旧版本的代码。

> ⚠️ 重要结论：**软件包更新完成 ≠ 运行中的进程已使用新版本。**
> 必须重启服务，进程才会加载新的二进制文件。
> 这解释了为什么"打了安全补丁但漏洞扫描仍然报警"。
>
> Ubuntu 可用 `needrestart -r l` 列出需要重启的服务。

**类型二：`3w` 类型——日志被删但进程仍在写**

```
unattended-upgrades  948  root  3w  REG  252,3  113  /var/log/.../xxx.log.1 (deleted)
```

`3w` = 文件描述符 3，以写模式打开。这正是 logrotate 轮转后
进程未释放旧句柄的真实案例，占用 113 字节。

体积虽小，但如果是几十 GB 的应用日志，就是典型的磁盘告警根因。

## 二、inode 耗尽

### 现象

磁盘还有大量剩余空间，但无法创建新文件，报错 `No space left on device`。

⚠️ 报错信息具有误导性——它说的是"没有空间"，
但 `df -h` 显示空间充足，容易被引向错误方向。

### 原理

文件系统在格式化时确定 inode 总数，每个文件/目录占用一个 inode。
空间和 inode 是**两套独立的配额**，任何一个耗尽都会导致无法写入。

本机基线：40G 分区共 2,608,144 个 inode，平均约每 16KB 一个。
若写入的都是小文件，inode 会先于空间耗尽。

### 复现方式

用文件模拟块设备，避免影响真实分区：

```bash
dd if=/dev/zero of=/tmp/disk.img bs=1M count=100
mkfs.ext4 -N 256 -F /tmp/disk.img       # 只分配 256 个 inode
mkdir -p /mnt/testdisk
mount -o loop /tmp/disk.img /mnt/testdisk

cd /mnt/testdisk
for i in $(seq 1 300); do touch file_$i 2>/dev/null; done

df -h /mnt/testdisk    # 空间几乎未使用
df -i /mnt/testdisk    # inode 100% 耗尽
touch newfile          # No space left on device
```

### 定位方法

```bash
df -i        # 确认是否 inode 耗尽

# 统计文件数量最多的目录
find /path -xdev -type f | wc -l
find /path -xdev -type d -exec sh -c \
  'echo "$(find "$1" -maxdepth 1 -type f | wc -l) $1"' _ {} \; \
  | sort -rn | head
```

⚠️ `-xdev` 表示不跨文件系统。生产环境查根分区时不加此参数，
会遍历到 /proc、网络挂载点等位置，既慢又不准确。

### 适用场景

大量小文件的业务场景尤其容易触发：
影像/图片存储、日志碎片、缓存文件、消息队列落盘文件等。
这类系统文件数量的增长速度远快于容量增长。

> ⭐ 实践原则：**排查磁盘问题时，`df -h` 和 `df -i` 应当同时执行。**

## 三、端口连通性排查

### ⭐ 分层排查链路（从内到外）

排查顺序必须由内向外逐层推进，每层用"通/不通"做二分，不可跳层。

```
第 1 层  服务是否在监听        ss -antlp | grep 端口
         ├─ 无输出 → 服务未启动，或监听在其他端口
         └─ 显示 127.0.0.1 → ⚠️ 仅绑定回环，外部无法访问（高频）

第 2 层  本机能否访问          curl 127.0.0.1:端口
         └─ 不通 → 应用层问题，不必继续查网络

第 3 层  内网 IP 能否访问      curl 内网IP:端口
         └─ 不通 → 绑定地址问题或本机防火墙

第 4 层  系统防火墙     ufw status / iptables -L -n
  └─ 存在 DROP/REJECT 规则 → 添加放行

第 5 层  云安全组 / 硬件防火墙  从外部 nc -vz IP 端口
         └─ timeout → 安全组未放行（高频）

第 6 层  客户端侧       本地策略、代理、实际出口 IP
```

### 监听地址的三种形式

| 监听地址 | 含义 |
|---|---|
| `0.0.0.0:8888` | 所有网卡，外部可访问 |
| `127.0.0.1:8888` | ⚠️ 仅回环，外部永远无法访问 |
| `[::]:8888` | IPv6 所有地址 |

"本机 curl 正常、外部无法连接"最常见的原因就是服务只绑定了 127.0.0.1。
许多框架的默认配置即为如此。

### 常用命令

```bash
ss -antlp | grep 端口     # -a全部 -n不解析 -t TCP -l监听 -p进程
lsof -i:端口
netstat -antlp | grep 端口   # 传统命令，老系统上可能只有它
```

## 四、⭐ TCP 连接失败的三种现象与判读

这是本次最有价值的收获，三种现象在实践中全部遇到过。

| 现象 | TCP 层行为 | 主要含义 | 排查方向 |
|---|---|---|---|
| **Connection refused** | 收到 RST | 端口无监听 | 服务层 |
| **Operation timed out** | 无任何响应 | 数据包被静默丢弃 | 网络层 |
| **连接建立但认证失败** | 三次握手完成 | 网络与服务均正常 | 应用层/凭据 |

### 核心区别

- **refused**：数据包**到达了**目标主机，内核明确回复 RST
  → 证明网络链路通畅、主机存活、内核正常工作，仅端口无服务
- **timeout**：数据包在中途被丢弃，根本没有到达
  → 网络路径存在阻断

⚠️ 这两者的排查方向完全相反。若混淆，会在错误的方向上浪费大量时间。

### ⚠️ 重要例外：refused 也可能是防火墙

防火墙有两种拒绝策略：

- `DROP`：静默丢弃，不返回任何响应 → 客户端表现为 **timeout**
- `REJECT`：明确返回 RST 或 ICMP unreachable → 客户端表现为 **refused**

内网环境（如企业/医院内部）的防火墙策略常使用 REJECT，
因为响应快、不让客户端长时间等待。

**因此 refused 不能直接等同于"服务没启动"。**

### ⭐ 区分"无监听"与"防火墙 REJECT"的对照测试

使用控制变量法，同时探测一个**已知不存在**的端口作为对照组：

```bash
nc -vz -w 3 目标IP 目标端口      # 待测端口
nc -vz -w 3 目标IP 45678  # 对照组：几乎不可能开放的端口
```

| 结果 | 判断 |
|---|---|
| 两者均 refused | 内核统一返回 RST，**目标端口确实无监听** |
| 待测 refused、对照 timeout | ⚠️ 防火墙对特定端口做了 REJECT 策略 |

### 探测工具

```bash
nc -vz -w 5 IP 端口       # 推荐，输出清晰

# 无 nc / telnet 时的兜底方案（bash 内置，几乎所有 Linux 可用）
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/IP/端口' \
  && echo "OPEN" || echo "CLOSED or FILTERED"
```

第二种方式不依赖任何额外工具，在被裁剪过的最小化系统上尤其有用。

## 五、⚠️ 出口 IP 陷阱（实际踩坑记录）

### 现象

配置云安全组的 IP 白名单时，通过 `curl https://ipinfo.io/ip`
查询到本机公网出口为 `A`，将 22 端口白名单配置为 `A/32` 后，
SSH 连接立即变为 timeout。

### 原因

服务端日志中记录的实际来源 IP 是 `B`，与 `A` 完全不同。

`curl` 查询走的是 HTTPS(443)，SSH 走的是 22 端口。
在存在代理、企业网关或多出口链路的网络环境中，
**不同协议/端口可能经由不同的出口 IP 访问外网。**

### ⭐ 正确做法

配置 IP 白名单时，**以服务端实际记录的来源 IP 为准**，
不要依赖第三方 IP 查询站点的结果。

```bash
last -i | head -10        # 历史登录来源 IP
grep "Accepted" /var/log/auth.log | tail -5    # Debian/Ubuntu
grep "Accepted" /var/log/secure | tail -5      # RHEL 系
who -u
```

同理，向第三方申请防火墙放行时，出口 IP 应当由
**对方从其防火墙日志中确认**，而非我方自行查询后告知。

## 六、⚠️ 变更远程访问配置的安全原则

> **修改任何影响远程访问的配置（云安全组、防火墙规则、sshd_config）时，
> 必须保持当前 SSH 会话不断开，另开新会话验证成功后，才关闭原会话。**

一旦配置错误，原有会话是唯一还能进入系统的通道。

同时应确认存在带外访问通道（云厂商的 VNC / Workbench 控制台），
作为最后的兜底手段。

本次修改安全组导致 SSH 中断，正是依靠云控制台的网页终端才得以恢复。

## 七、命令速查

### 磁盘

```bash
df -h       # 空间（注意精度限制）
df -m       # 空间，MB 精度
df -i# ⭐ inode，与 df -h 配套使用
du -sh /* | sort -h | tail -10     # 定位大目录
lsof +L1    # ⭐ 已删除但仍被占用的文件
find /path -xdev -type f | wc -l   # 统计文件数
```

### 网络

```bash
ss -antlp | grep 端口   # 监听状态与进程
ss -s     # 连接状态汇总
lsof -i:端口
nc -vz -w 5 IP 端口     # 端口探测
sar -n DEV 1 3          # 网卡吞吐
sar -n TCP,ETCP 1 3     # TCP 重传
```

### 进程与资源

```bash
vmstat 1 5       # 整体（跳过第一行）
mpstat -P ALL 1 3       # 各核均衡性
pidstat 1 3      # 进程级资源占用
iostat -xz 1 3   # 磁盘 IO
dmesg -T | tail -20     # 内核日志
```

## 八、本次实践的三点方法论收获

1. **验证实验设计本身是否成立**
   `>>` 每次重新打开文件，无法复现句柄持有场景。
   若不先确认实验能够反映目标机制，得到的结论是无效的。

2. **确认观测精度是否足够**
   `df -h` 的精度掩盖了 MB 级变化。
   "指标没有波动"可能只是量具不够精确，而非真的没有变化。

3. **区分现象的细微差异**
   refused 与 timeout 仅一词之差，指向的排查方向完全相反。
   排查中最关键的往往不是知道更多命令，而是能准确解读现象。
