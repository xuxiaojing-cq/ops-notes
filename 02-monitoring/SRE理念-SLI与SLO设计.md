# SRE 核心理念：SLI / SLO / 错误预算与告警设计

> 学习日期：2026-09-10
> 实践环境：Ubuntu 22.04 ECS

## 一、SRE 要解决什么问题

> SRE 是用软件工程的方法解决运维问题。

三个核心转变：

| 传统运维 | SRE |
|---|---|
| 追求「不出故障」 | **接受故障必然发生**，控制影响范围 |
| 稳定性依赖人工盯守 | 稳定性依赖系统性设计 |
| 出问题后被动处理 | **用数据决定何时该介入** |

### ⭐ 100% 可用性是错误的目标

这是 SRE 最反直觉也最重要的观点，理由有三：

1. **成本非线性上升**
   从 99.9% 提升到 99.99%，投入可能增加十倍，
   而用户几乎无法感知差异。

2. **用户链路本身不是 100%**
   终端设备、浏览器、中间网络的可用性加起来
   可能只有 99%。服务端做到 99.999% 对用户没有意义。

3. ⭐ **追求零故障会扼杀迭代**
   任何变更都有风险。如果不允许出错，
   最理性的策略就是什么都不改——但业务会因此停滞。

> 因此 SRE 的目标不是消灭故障，
> 而是**在可接受的故障范围内，最大化迭代速度**。

## 二、SLI / SLO / SLA

```
SLI (Indicator)  指标：衡量服务质量的具体数字
   ↓
SLO (Objective)  目标：该指标应达到的水平（内部目标）
   ↓
SLA (Agreement)  协议：未达标需赔偿（对外合同，有法律效力）
```

⚠️ **SLO 必须严于 SLA**。若合同承诺 99.5%，
内部目标应定为 99.9%，留出处置缓冲。

### ⭐ SLI 的本质

> SLI 是把「服务好不好」翻译成一个双方都认可的数字。

⚠️ 若 SLI 定义不清，各方对「服务是否正常」的判断会持续冲突。
这与跨系统数据核对中的口径对齐是同一类问题：
**定义先于测量**。

### 四个黄金信号

| 信号 | 含义 |
|---|---|
| Latency | 请求耗时 |
| Traffic | 请求量 |
| Errors | 失败率 |
| Saturation | 资源接近极限的程度 |

⭐ 与 USE 方法的区别在于视角：

- **USE**（Utilization / Saturation / Errors）→ 从**资源**看
- **四个黄金信号** → 从**服务**看，即用户实际感受

**SLI 必须采用后者。** 资源指标正常不代表服务正常
（例如进程存活但未产出数据）。

### ⭐ SLI 的标准写法

```
SLI = 好事件数 / 有效事件总数
```

**必须是比例，不能是绝对值。**

- ❌ `每日失败少于 100 条`
- ✅ `成功数 / 应处理总数 ≥ 99.5%`

⚠️ 绝对值随业务量变化会失去意义：
日处理量 1000 时失败 100 条是灾难，
日处理量 100 万时失败 100 条是正常波动。

### ⭐⭐ 分母必须独立于被测系统

这是 SLI 设计中最容易犯的错误。

| | 说明 |
|---|---|
| ❌ 错误 | 分母 = 系统已处理的记录数 |
| ✅ 正确 | 分母 = 源头应处理的记录总数 |

⚠️ 若分母来自系统自身的处理结果，
则系统故障时分母同步变小，SLI 反而更好看——
**未被处理的数据根本不在统计范围内**。

分母必须来自数据源头，例如上游数据库的记录总数。

## 三、错误预算（Error Budget）

```
错误预算 = 1 - SLO
```

### 换算表（30 天周期）

| SLO | 允许不可用时长 |
|---|---|
| 99% | 7 小时 18 分 |
| 99.5% | 3 小时 39 分 |
| **99.9%** | **43 分钟** |
| 99.95% | 21 分钟 |
| 99.99% | 4 分 23 秒 |

### ⭐ 核心价值

错误预算把「要稳定还是要迭代」这一长期争论
转化为一个可判定的数字：

```
预算有剩余 → 可以发布变更、承担风险
预算已耗尽 → 冻结非必要变更，优先修复稳定性
```

⭐ 这消除了开发与运维的立场对立——
不再是「谁说服谁」，而是「看预算说话」。

### ⭐ 实测：百分比会麻痹判断

本次实验数据：

```
总请求 2000，失败 41
实际 SLI  97.95%
目标 SLO  99.50%
错误预算总额 10 条
已消耗      41 条
预算消耗率  410%
```

⚠️ **97.95% 与 99.5% 直觉上「只差一点」，
但在错误预算尺度上是 4 倍超支。**

> 用百分比看问题会低估严重性，
> 用错误预算看问题才有正确的紧迫感。

### ⚠️ 统计窗口决定指标是否有管理意义

同一组故障数据，窗口不同结论完全不同：

| 场景 | 年度统计 | 月度统计 |
|---|---|---|
| 全年中断 2 天 | 99.45%，看似达标 | 故障月 93.3%，预算超支数十倍 |

⚠️ **长窗口会把灾难摊薄成背景噪音。**
对不可接受单日中断的业务，
统计窗口应为天或月，年度平均值没有管理价值。

## 四、告警设计

### ⭐ 核心原则：基于症状告警，而非原因

| | 原因型告警 | 症状型告警 |
|---|---|---|
| 示例 | CPU > 80% | 处理成功率 < 99% |
| 问题 | 资源高不一定影响用户 | 直接反映用户受损 |
| 覆盖范围 | 仅覆盖已预想到的原因 | ⭐ **覆盖全部失败模式** |

⭐ 症状型告警的关键优势：
**无需预先枚举所有失败原因。**

不论是网络中断、下游存储故障、程序缺陷还是资源耗尽，
最终都会表现为「成功率下降」。

### ⚠️ 典型反面案例：只监控链路前半段

```
链路：源系统 → 采集 → 上传 → 目标存储

只监控「采集量」（原因型，前半段）
    ↓
上传环节故障时采集量仍正常
    ↓
指标无异常，无告警
    ↓
最终由用户反馈才发现
```

⭐ 正确做法是监控**端到端一致性**：
`源头记录数` 与 `最终落地记录数` 的差值。
这个指标不关心中间哪个环节出问题，
只要两端对不上就会暴露。

⚠️ 实现时需考虑处理延迟，
按合理周期（小时/天）比对，避免正常延迟被误判。

### 一条有效告警必须满足

1. **用户受影响了吗？** 否 → 不应告警，降级为日报或工单
2. **需要人立即介入吗？** 否 → 不应触发即时通知
3. **收到后知道做什么吗？** 否 → 应附带处置文档链接

### ⭐⭐ 告警疲劳本身就是一种故障

判断标准：

> 如果告警触发后，值班人员的第一反应是「这个不用管」，
> 那么该告警应当被删除或改造。

⚠️ 它不仅没有价值，还在持续消耗人对告警系统的信任。
**代价是真实故障被一并忽略。**

### ⭐ 常见根因：通用规则应用于不适用的业务场景

一个典型模式：
监控规则对全部业务类型统一校验，
但部分类型在业务上本就不满足该规则，
导致持续产生无效告警。

**正确的改造方向不是删除告警，而是按业务类型拆分规则**，
使规则的适用范围与业务规范一致。

⚠️ 前提是数据中存在可用于分类的字段，
且该字段取值已标准化。
若上游系统取值不统一，需先做统一映射。

## 五、延迟 SLI 必须使用分位数

### ⭐ 平均值会掩盖灾难

假设 99% 的请求耗时 100ms，1% 的请求耗时 60s：

```
平均值 ≈ 700ms   看起来正常
P99   = 60000ms  实际有 1% 用户体验极差
```

⚠️ **服务异常时受影响的往往正是那一小部分请求**，
而平均值恰好会把它稀释掉。

### 计算方法

```bash
grep "SUCCESS" collect.log | grep -o 'cost=[0-9]*' | cut -d= -f2 | sort -n > costs.txt
n=$(wc -l < costs.txt)
for p in 50 90 95 99; do
  idx=$(( n * p / 100 ))
  echo "P${p}: $(sed -n "${idx}p" costs.txt) ms"
done
```

⭐ 常用组合：P50 看典型体验，P99 看最差体验，
两者差距过大说明存在长尾问题。

## 六、⭐ 时间戳的正确记录方式

### 存端点，不存差值

计算「处理耗时」这类指标时：

| | 做法 | 评价 |
|---|---|---|
| ❌ | 程序直接记录「总耗时」字段 | 口径写死，调整需改代码 |
| ✅ | 记录起止两个时间戳 | ⭐ 查询时相减，口径可随时调整 |

```
耗时 = 完成时间戳 - 起始时间戳
```

⚠️ **只要两个端点的时间戳都有记录，
差值指标就是现成可算的，不需要新增埋点。**

这是一个常见误判：
以为「没有耗时字段」等于「无法统计耗时」，
实际上只是缺一次减法。

### ⚠️ 前提：时钟同步

跨系统计算时间差时，两端必须使用同一时钟源。
若上下游服务器时间不同步，差值会失真甚至为负。

```bash
timedatectl status
ntpstat
chronyc sources
```

## 七、故障管理

### Blameless Postmortem（无指责复盘）

⭐ 核心不是「对人宽容」，而是基于一个现实：

> 若复盘会追究个人责任，参与者就会隐瞒细节。
> 信息不完整则无法定位系统性缺陷，
> 同类故障必然重演。

**正确的转化方式：**

| 归因方式 | 结果 |
|---|---|
| ❌ 「某人不够细心」 | 换个人还会再犯 |
| ✅ 「监控未覆盖该环节」 | 补上监控后彻底消除 |

⭐ 判断标准：**改进项是否能在人员变动后依然生效。**

### 复盘报告必备内容

1. 影响范围（受影响对象、持续时长、受损业务）
2. 时间线（发现 / 响应 / 定位 / 恢复的具体时刻）
3. 根因分析（至少追问三层为什么）
4. 处置措施
5. ⭐ 改进项（**必须有责任人和完成时间**）

⚠️ 缺少第 5 项的责任人与时间点，复盘报告即无效。

### ⭐ MTTR 的拆解

```
MTTR = 发现时间 + 定位时间 + 修复时间
```

⚠️ 多数团队专注于缩短「修复时间」，
但真正的瓶颈通常在「发现时间」。

**典型分布：**

| 阶段 | 耗时量级 |
|---|---|
| 发现（依赖用户反馈时）| 小时 ~ 天 |
| 定位 | 小时 |
| 修复 | 分钟 ~ 小时 |

⭐ **优化发现时间的收益远大于优化修复时间。**
这也是可观测性建设优先级最高的原因。

## 八、实践小结

### 从日志计算 SLI 的完整流程

```bash
# 1. 可用性
total=$(wc -l < collect.log)
success=$(grep -c "SUCCESS" collect.log)
awk -v s=$success -v t=$total 'BEGIN{printf "SLI = %.4f%%\n", s/t*100}'

# 2. 错误预算消耗
SLO=99.5
budget=$(awk -v t=$total -v s=$SLO 'BEGIN{printf "%.0f", t*(100-s)/100}')
used=$((total-success))
awk -v u=$used -v b=$budget 'BEGIN{printf "预算消耗率 %.1f%%\n", u/b*100}'

# 3. 失败原因分布（排查入口）
grep "FAILED" collect.log | grep -o 'reason=[a-z_]*' | sort | uniq -c | sort -rn
```

⭐ 第 3 步在实际工作中价值最高：
失败原因的分布变化本身就是排查方向。
若某类原因占比突然上升，
无需等待用户反馈即可判断问题层面。

### 三个核心认知

1. ⭐ **100% 可用性是错误的目标**
   错误预算把稳定性与迭代速度的矛盾变为数字判断

2. ⭐ **基于症状告警而非原因**
   症状型告警可覆盖所有未预料到的失败模式

3. ⭐ **延迟必须看分位数**
   平均值会掩盖少数用户的灾难性体验

### ⚠️ 一个通用的观测缺陷模式

```
只统计成功数，不统计失败数与总数
    ↓
无法计算成功率
    ↓
故障时指标仅表现为「数量下降」
    ↓
无法区分「无人使用」与「全部失败」
```

⭐ 任何服务的观测设计都应确保
**分子与分母同时可得**，否则无法定义 SLI。
